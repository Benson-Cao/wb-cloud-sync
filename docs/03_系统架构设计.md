# 03 系统架构设计（HLD + ADR）

> Owner：架构师 ｜ 版本 v1.0 ｜ 状态：已冻结
> 契约源：`04_接口协议与数据模型.md`

---

## 1. 架构原则

| 编号 | 原则 | 含义 |
|---|---|---|
| P1 | **一个会话、多个视图、一个写入者** | `~/.dsh` 事件日志是唯一真源；手机只是投影 |
| P2 | **执行留在 PC** | 云不做 Agent、不跑模型、不存工作区 |
| P3 | **云只管索引与路由** | CP 存账号/设备/SessionIndex/Route/Cursor，不存事件正文 |
| P4 | **Host 主动外连** | PC 零入站端口，符合企业合规 |
| P5 | **协议优于实现** | Relay 只做帧透传，不解析会话语义 |
| P6 | **不 fork DSH** | 一切通过 Cordis 插件接缝（`inject` / `effect` / `webServer` / `sessionPersistence`） |
| P7 | **可逆副作用** | 路由、监听、定时器、WS 连接一律交 `ctx.effect` 清理 |

## 2. 总体架构

```
┌──────────────┐   ┌──────────────┐
│ 手机 PWA     │   │ 第三方客户端 │  ← 依据 PROTOCOL.md 接入
└──────┬───────┘   └──────┬───────┘
       │ HTTPS / WSS       │
       ▼                   ▼
┌─────────────────────────────────────────────┐
│ 云端控制面 CP                                │
│  ├─ OAuth (Google / GitHub)                  │
│  ├─ Account / Settings / Memory / Automation │
│  ├─ DeviceRegistry (online, name, caps)      │
│  ├─ SessionIndex (lastSeq, state, pinned)    │
│  ├─ RouteLease (session → host)              │
│  └─ Cursor (client → sinceSeq)               │
└──────────────────┬──────────────────────────┘
                   │ 注册 / 索引查询 / 令牌校验
┌──────────────────▼──────────────────────────┐
│ Relay（自托管，可独立部署）                  │
│  /pair  配对码 → 挑战 → HMAC → 令牌          │
│  /d/<deviceId>/*  HTTP 反向代理（帧保序）    │
│  /events/*        WS 透传                   │
│  /admin           设备总览 / 吊销             │
└──────────────────┬──────────────────────────┘
                   │ WS 长连（Host 主动注册）
      ┌────────────┴────────────┐
      ▼                         ▼
┌─────────────────┐     ┌─────────────────┐
│ PC-A  Host      │     │ PC-B  Host      │
│ DSH (web profile)│     │ DSH (web profile)│
│ └ wb-cloud-sync │     │ └ wb-cloud-sync │
│   ├ host 半边   │     │   ├ host 半边   │
│   └ client 半边 │     │   └ client 半边 │
│ ~/.dsh 事件日志 │     │ ~/.dsh 事件日志 │
└─────────────────┘     └─────────────────┘
```

**三层信任边界**：手机 ↔ CP（账号鉴权）／ CP ↔ Relay（服务间信任 + `HOST_TOKEN`）／ Relay ↔ Host（设备令牌 + 挑战响应）。Relay 跨在中间但**不理解会话内容**（"不解析 / 不落盘" ≠ "不可见"；TLS 在 Relay 终止，见 `04` §5.4 / ADR-010）。

## 3. 组件职责

### 3.1 Host 插件 `dsh-wb-cloud-sync`（bundle）

- 形态：函数式 Cordis 插件，`export const name`、`inject = ['webServer', 'sessionPersistence']`、`apply(ctx, config)`。
- 配置：`Schema.object({ relayUrl: Schema.string().required(), hostToken: Schema.string().required(), autoConnect: Schema.boolean().default(true) })`。
- 职责：
  1. 启动注册到 Relay（host/register + 全量会话索引）。
  2. 订阅 `session/event` → 原样透传（携带会话内 `seq`）。
  3. 上报 `lastSeq` / `state` 增量到 CP。
  4. 处理 `session/prompt`（幂等后交宿主会话 owner 写入）、`session/cancel`、`$events/result`。
  5. 注册本地具名路由供 client 半边与配对页使用。
  6. 所有注册交 `ctx.effect`，卸载即撤回。
- **关键约束**：绝不 `open(sessionId, 'write')`。手机投递只走宿主提供的提交入口；若宿主未暴露该入口，W1 Spike 必须解决，不得以"自己追加日志"绕过单写者。

### 3.2 Client 半边（`dsh.client`）

- 提供设置页「手机连接」（relay 地址、HOST_TOKEN、自动连接、配对码展示）与侧栏快捷按钮。
- 包元数据在进程内有缓存，**首次安装后需重启一次 DSH** 才出现。
- 只有 `dsh.client` 没有 `dsh.bundle` 的包不会自动激活；两半必须同时声明。

### 3.3 Relay

- 配对：6 位码（10 min TTL，设备 + IP 限速 5 次/分）→ 一次性挑战（60s）→ HMAC-SHA256 → 令牌；持令牌静默重连。
- 传输：请求/响应按 ≤ 64KiB 帧搬运，**帧序即流序**，SSE / blob 不受影响；`/events/*` 的 WebSocket upgrade 转为 `ws-open / ws-frame / ws-close` 帧透传。
- 保护：Host 离线立即 409；10s 无进度防悬挂；单活跃令牌（**逐设备**：手机自成一设备行，r9 起一台 Host 可绑多台手机）；孤儿与 30 天前已吊销令牌加载时清理；删除设备写真墓碑。
- `/manifest.webmanifest` 必须无鉴权静态提供（浏览器拉取 manifest 不带 cookie，无法走代理）。
- 管理台 `--admin-token` 启用：设备总览、配对码有效期、令牌指纹、断开/吊销/删除、在线筛选。

### 3.4 CP 控制面

- OAuth 账号主体；账号级同步设置、Memory、自动化定义、Assistant 配置。
- `DeviceRegistry`、`SessionIndex`、`RouteLease`、`Cursor` 四张元数据表（Postgres）。
- 提供设备列表、会话索引查询、索引写入（Host 上报）、令牌校验回调给 Relay。
- **不存事件正文、不存文件**。

### 3.5 手机 PWA

- 设备选择 → 会话列表（含状态点）→ 对话页（事件渲染 + 队列输入 + 停止按钮）→ 产物列表 / 审批面板。
- 纯 Dart/TS 客户端分层思路借鉴 dsh-Go：`packages/client` 做纯协议客户端，UI 与协议解耦，便于单测与第三方复用。

## 4. 关键数据流

### 4.1 配对与建连

```
PC 设置页"生成配对码" → CP 登记(码, deviceId, TTL)
手机输入码 → Relay /pair → 返回 challenge(60s)
手机 HMAC(token_seed, challenge) → Relay 校验 → 签发 deviceToken
Relay 落 SHA-256(token) 摘要，作废旧活跃令牌
手机携 token 静默重连；Host 侧 WS 早已注册在 Relay
```

### 4.2 手机发消息

```
PWA POST /d/<deviceId>/session/prompt {sessionId,text,clientMsgId}
 → Relay 帧代理 → Host 插件
 → clientMsgId 映射为宿主 requestId；宿主按 source.rpcId 原生去重，重复返回 {accepted:true}
 → 宿主会话 owner 独占 write 句柄；第二写者抛 SessionAlreadyOwnedError → 409 ROUTE_CONFLICT
 → owner 写入 → DSH 追加 user/message(seq=N)
 → session/event(N) 广播 → Relay → 所有订阅客户端（含 PC 自身视图）
 → CP 更新 lastSeq=N / state=running
```

### 4.3 PC 端输出回流

```
DSH agent loop emit assistant/chunk / assistant/message / tool/call / tool/result ...
 → Host 插件透传（seq 原样）
 → Relay WS 帧 → 手机
 → 手机按 Surface 规则折叠：chunk 累积成最终 assistant/message，
   tool/call + tool/result 配对展示，turn/step 作过程条
```

### 4.4 断线补齐

```
手机重连 GET/WS follow?sinceSeq=K
 → Host 从本地日志读连续前缀 (K, N]（read-only open，只读不写）
 → 按 seq 顺序补发；客户端幂等丢弃 seq <= K
```
> 注意：`open(id, 'read')` 返回经验证的连续前缀切片，绝不返回撕裂尾部；重复读不会看到更旧状态。

### 4.5 审批

```
DSH 需要审批 → Host 发 $events/approval 到手机 + 桌面端
任一端作答 → $events/result → Host 回注 → agent loop 继续
琥珀状态点清除
```

## 5. 部署视图

| 组件 | 部署位置 | 对外端口 | 备注 |
|---|---|---|---|
| CP | 云主机 B | 443 | OAuth 回调、REST |
| Relay | 云主机 A | 443 | WS 长连，内存敏感 |
| Postgres | 云主机 B | 内网 | 仅元数据 |
| Host 插件 | 用户 PC | **无入站** | 主动 WSS 外连 |
| PWA | 静态托管 / Relay | 443 | manifest 无鉴权 |

PC 需开启「允许移动端连接此设备」与「保持唤醒 / 锁屏可运行」；macOS 还需「合盖不睡眠」。

## 6. 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| Host 插件 | TypeScript + Cordis + schemastery | DSH 原生，不 fork |
| 本地路由 | `ctx.webServer.register` exact/prefix | 支持长连 SSE，disposer 可逆 |
| 配置 | `Schema.object` | Cordis 加载时校验并补齐默认值，不手写 zod |
| Relay / CP | Node.js ≥ 22（Relay）/ 24.9（构建链）+ TypeScript | 与 DSH 工具链一致；Relay 用原生全局 WebSocket |
| 存储 | Postgres（CP 元数据） | 事务性 RouteLease / Cursor |
| 手机端 | PWA + TS | v1 不碰原生，覆盖 iOS/Android |
| 构建 | pnpm 11 + esbuild | 与社区插件发布流水线一致 |
| 分发 | npm（`dsh plugin --profile web add <tgz>`） | 官方 bundle 安装路径 |

## 7. 备选方案与否决理由

| 方案 | 否决理由 |
|---|---|
| 网盘/文件双向同步 `~/.dsh` | 追加式日志会被撕裂；与单写者、resume 语义冲突 |
| 云端存会话正文做"全端一致" | 违反 P2/P3，隐私合规不过，成本高 |
| 手机跑本地 DSH 引擎（PRoot） | 工程量大、侧载分发、与"执行留 PC"目标不符 |
| SSH 直连 / `dsh web` token URL | 需同网络或手工端口转发，无账号级设备发现 |
| 直接 fork DSH 加远程模块 | 上游 Developer Preview 频繁变更，维护成本不可控 |

## 8. 附录：架构决策记录（ADR）

### ADR-001 会话真源与写入权
- **状态**：已接受
- **决策**：`~/.dsh` append-only `SessionEvent` 日志为唯一真源；每会话单写者（Route Lease）；手机只投递不写。
- **理由**：DSH 持久化层对同一会话的并发 `open(id,'write')` 直接抛 `SessionAlreadyOwnedError`；双写会撕裂日志。崩溃由 resume 追加 `interrupted` 收尾，持久化层不自修。
- **后果**：跨 PC 会话迁移 v1 不支持；需新增 RouteLease 表与 409 语义。

### ADR-002 云端只存元数据
- **状态**：已接受
- **决策**：CP 不存事件正文与工作区文件，只存 SessionIndex / Route / Cursor / 设备与账号数据。
- **理由**：对标 WorkBuddy 的本地执行模型；文件留在 PC 是隐私与合规底线，也省存储带宽。
- **后果**：手机查看历史消息必须连上对应在线 PC；离线只能看索引与状态。

### ADR-003 Host 主动外连 Relay
- **状态**：已接受
- **决策**：PC 不开入站端口，WSS 主动注册到 Relay；Relay 做反向代理与帧透传。
- **理由**：企业网络常禁入站；host 离线可立即 409，避免悬挂。
- **后果**：Relay 成为可用性单点，需 SLO 与自托管多实例方案（v2）。

### ADR-004 seq 作为唯一游标
- **状态**：已接受
- **决策**：断线补齐用会话内连续 `seq`，禁止时间戳；Relay 帧序即流序。
- **理由**：`seq` 等于 `log.length`、连续无间隙，每条事件自带，天然幂等与有序。
- **后果**：客户端必须做 `seq <= sinceSeq` 丢弃；跨会话游标独立。

### ADR-005 不 fork DSH，锁 commit
- **状态**：已接受
- **决策**：基于 pinned commit 开发，所有能力经插件接缝；升级单独立 ADR。
- **理由**：DSH 处于 Developer Preview，官方明示会有不兼容变更；上游虽已开始使用 release tag，仍无稳定版承诺，且版本间可能有破坏性变更。
- **后果**：W1 必须做 Spike 验证接缝可用；上游升级需回归全量 E2E。

### ADR-006 PWA 优先于原生 App
- **状态**：已接受（v1）
- **决策**：v1 只做 PWA，客户端协议层独立成包。
- **理由**：覆盖双平台、无审核/侧载成本；协议层可复用为未来的原生客户端。
- **后果**：iOS 后台保活与通知受限，需产品层说明；v2 评估原生。

### ADR-007 事件契约以宿主实测为准
- **状态**：提议中（待 ARC + PM 会签）
- **决策**：`04` §3 以 DSH 0.2.2-rc.1 实测为准：事件基形 `type/seq/time/data`，扩展字段 `surfaceOp`、`sourceEventSeqs` 可选；日志无 `assistant/chunk`、无 `ignorable`；客户端采用「白名单投影 + 未知默认跳过」；`sourceEventSeqs` 仅用于 `tool/result` ↔ `tool/call` 配对。
- **理由**：W1 Spike 在 667 条真实事件上取证，v1.0 的 chunk 折叠与 ignorable 规则与宿主不符；`surfaceOp` 是宿主自带投影指令，客户端自行重算会与之冲突。
- **后果**：`02` FR-4.2/4.3、`04` §3、`07` TC-1.2/1.3 同步修订；`SessionEvent` 仅新增可选字段，属兼容变更，协议仍为 `wbsync/1`。

### ADR-008 幂等与写入权归宿主
- **状态**：提议中（待 ARC + PM 会签）
- **决策**：`clientMsgId` 直接映射宿主 `prompt(request).requestId`；Host 侧不建 `Idempotency` 表、不自开 `open(id,'write')`；`RouteLease` 在 CP 侧仅作跨 Host 路由元数据与审计，不承担进程内写入权仲裁。
- **理由**：宿主 `dsh-api-session-controller` 的 `hasPromptRequest()` 按 `source.rpcId` 原生去重，`SessionAlreadyOwnedError` → `session/writer-held` 已是硬约束；平台重复实现会产生两套真源。
- **后果**：`04` §1/§2、`03` §4.2、`02` FR-4.5 修订；`03` §3.1 与 `06` §3.3「绝不 open(id,'write')」铁律保持不变。

### ADR-009 PROTOCOL.md 为唯一契约源
- **状态**：提议中（待 ARC 会签）
- **决策**：仓库根 `PROTOCOL.md` 是 `04` 的**发布副本**，由 `04` 单向同步；字段变更必须在同一 PR 同时改 `04` + `PROTOCOL.md` + `CHANGELOG.md` 并升修订号，CI 校验三者 diff 同时存在。
- **理由**：`01` G9、`06` §2/§9 对 PROTOCOL.md 的归属表述不一，第三方客户端（`02` §6 第 16 项）需要唯一入口。
- **后果**：新增 `scripts/sync-protocol.mjs` 单向同步脚本；`06` §9 补充「不得独立编辑 PROTOCOL.md」规则。

### ADR-010 正文可见性边界（at-rest 与 in-transit 分开承诺）
- **状态**：提议中（待 ARC + 安全 Owner 会签）
- **决策**：`04` §5.3 的上行 `session/event` 帧携带 `ev.data`（会话正文），TLS 在 Relay 终止，因此 **Relay 进程可见明文事件帧**。v1 只承诺「CP 无正文表、Relay 不写盘、正文不进入任何持久化层」与「工作区文件 0 字节经过 Relay/CP」；**不承诺对 Relay 运维的机密性**。项目所有「会话正文不上云」统一按此解释。
- **理由**：`wbsync/1` 事件流必须把正文送到手机才能渲染，且 Relay 需终止 TLS 做路由；把「不落盘」写成「不可见」会让 `08` §6、`07` TC-7.6 的出网审计目标必然失败，属于会签时给出的错误承诺。WorkBuddy 官方同样把「对话内容与任务记录」列为必要收集项，保护手段是传输加密（见 `WORKBUDDY-REFERENCE.md` §3.1）。
- **后果**：正文机密性依赖自托管 Relay + 运维可信 + 主机加固（`10` §6），不依赖密码学隔离；`02` NFR-4、`08` §2/§6/§10、`07` TC-7.6 口径同步收敛；若要求「Relay 被攻破也拿不到正文」，须引入 Host↔手机端到端加密载荷（`enc` 字段 + 配对期密钥交换），属不兼容变更，升 `wbsync/2` 并单独立 ADR，**v1 不做**。
