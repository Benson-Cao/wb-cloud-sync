## 2. 红色风险专项应对

### R-01 DSH 不兼容变更
- **预防**：`pinned-commit.txt` 入库，CI 校验；不 `pnpm update` 生产 profile。
- **监测**：订阅上游仓库变更；每次里程碑前跑一次"上游 diff 影响面"快评。
- **应急**：升级单独立项 → 契约测试 → E2E 全量 → 新 ADR → 灰度 → 才允许合入。
- **兜底**：若某接缝彻底移除，回退到 v0 能力集（只读镜像），并对外公告兼容性矩阵。

### R-02 宿主提交入口缺失（**P0 门禁项**）
- W1 Spike 必须回答三个问题并留可运行证据：
  1. 能否订阅到带连续 `seq` 的会话事件？
  2. 能否在不打开写句柄的前提下，把一条用户消息交给当前轮次的 owner？
  3. `sessionPersistence.list()` / `open(id,'read')` 能否枚举与只读回放？
- **判定**：三问全过才进 P1。任一不过，当天上报发起人，启动方案 B（上游 issue / 收缩范围），**不允许"先写日志再说"**。

- **2026-11-07 离线取证结论**：三问全 PASS —— Q1 事件 `seq` 0→666 连续；Q2 宿主 `dsh-api-session-controller.prompt(request)` 提供提交入口，自带 `requestId` 幂等与 `SessionAlreadyOwnedError` 单写者；Q3 `list()` / `open(id,access)` / `persistContiguous` 齐备，`sinceSeq=400` 补齐 266/266。证据见仓库 `spike/REPORT.md`。**真机加载与事件闭环已于 18:34 全 PASS**（见仓库 `spike/REPORT.md` §4.1.2），三问判 PASS，风险待四方会签后关闭。

### R-06 PC 在线依赖
- 这是架构选择的必然代价（执行留 PC），不是 bug。
- 缓解以**预期管理**为主：首次连接引导页把「开机 / 联网 / 允许连接 / 保持唤醒」四项做成检查清单；手机端设备卡片直接显示在线/离线与最后在线时间。

## 4. 上报规则

- 红色风险状态变化 **24 小时内**上报发起人。
- 风险值 ≥ 15 且缓解失效 → 立即暂停对应模块合入，PM 召集决策会。
- 所有新识别风险当日入表，不允许"先记在群里"。
