## 3. Cordis 插件编写规范

### 3.1 形态选择

- 绝大多数场景用**函数形态**（具名导出 `name` + `apply`），官方原话 "Function form is sufficient in most cases"。
- 需要对外长期持有服务时才用 `Service` 类形态。
- **函数形态具名导出与对象/类形态默认导出不可混写**：既写 `export default` 又写具名 `apply`，框架只看一种，另一半声明会被静默忽略。
- `name` 唯一且可读，禁止 `plugin` / `main` 这类通用词；它用于 `cordis.yml` 条目引用与故障定位。

### 3.2 最小骨架

```ts
// packages/host-plugin/src/index.ts
import type { Context } from '@deepseek-ai/cordis'
import Schema from '@deepseek-ai/schemastery'

export const name = 'wb-cloud-sync'
export const inject = ['webServer', 'sessionPersistence']

export interface Config {
  relayUrl: string
  hostToken: string
  autoConnect: boolean
  allowedEndpoints: string[]
}
export const Config: Schema = Schema.object({
  relayUrl: Schema.string().required(),
  hostToken: Schema.string().required(),
  autoConnect: Schema.boolean().default(true),
  allowedEndpoints: Schema.array(Schema.string()).default(['session/*', '$events/*']),
})

export function apply(ctx: Context, config: Config) {
  // 所有注册交给 ctx.effect，卸载自动清理
  ctx.effect(() => {
    const ws = connectRelay(config.relayUrl, config.hostToken)
    const off = ctx.on('session/event', (session, ev) => {
      // 实测：首参是 session 对象，不是 sessionId 字符串
      ws.send({ t: 'session/event', sessionId: session.header.id, ev })  // 原样透传 seq
    })
    return () => { off(); ws.close() }
  })
}
```

### 3.3 五条铁律

1. **依赖用 `inject` 声明**，不要在 `apply` 里轮询等待服务；Cordis 会等依赖就绪才加载。也可 `ctx.inject(['commands'], scoped => ...)`。
2. **所有注册都是 effect**：`ctx.on()`、`ctx.effect(() => disposer)` 自动清理。手动定时器 / 监听 / WS 必须写成 `ctx.effect(() => { const t = setInterval(...); return () => clearInterval(t) })`，否则热重载泄漏。
3. **`register()` 返回 disposer 必须交 `ctx.effect()`**，插件卸载时路由自动撤回。
4. **配置用 schemastery，不用 zod**：默认值写在 schema 里，Cordis 加载时校验并补齐；`apply(ctx, config)` 拿到的永远是全量配置。不要导出普通对象当 `Config`。
5. **绝不 `open(sessionId, 'write')`**：单写者租约是硬约束，第二个写句柄抛 `SessionAlreadyOwnedError`。手机投递必须交宿主会话 owner 的提交入口。

### 3.4 路由规范

```ts
ctx.effect(() => ctx.webServer.register({
  kind: 'exact', path: '/__wbsync/status',
  handler: async (req, res) => { /* ... */ },
}), 'wbsync: status route')
```

- 只有 `exact`（逐字匹配）与 `prefix`（前缀本身及其下子路径）两种。
- 匹配顺序固定：全表 exact → 最长前缀 → 回退处理器；**注册顺序不携带请求语义**。
- 重复注册同 `kind + path` 直接抛异常（组合层契约，冲突即配置错误）；回退席位全局唯一，本项目不注册。
- 处理器可一直挂着连接，SSE 推流即此用法。
- Electron 桌面端经 `file://` 加载构建产物 + IPC 桥转发 fetch，**不经过本地 HTTP server**；client 半边需适配该链路。

## 4. 配置分发与 bundle

```jsonc
// package.json
{
  "name": "dsh-wb-cloud-sync",
  "version": "0.1.0",
  "type": "module",
  "main": "dist/index.js",
  "files": ["dist", "client", "cordis.patch.yml"],
  "dsh": {
    "bundle": { "patch": "./cordis.patch.yml" },
    "client": { "entry": "./client/index.js" }
  }
}
```

- `dsh.bundle` 说明包贡献哪层配置 patch；`dsh plugin add` 只有看到它才把包加入 profile 的 bundle stack。
- `dsh.client` 说明该 Loader entry 还有浏览器半边，由 Client module host 发现。
- **只有 `dsh.client` 没有 `dsh.bundle` 的仓外包只作为普通依赖安装，不会自动激活**。
- client 半边包元数据在进程内有缓存，**首次安装后需重启一次 DSH**。
- `cordis.patch.yml` 用稳定 row id（`wb-cloud-sync`），便于后续 profile patch 覆盖；包内 rows 引用包名而非源相对路径。
- Profile 组合顺序：bundle patches（按序）→ profile patch → machine patch → CLI patch overlays；后层可替换前层 row。

### 打包与安装

```bash
pnpm install && pnpm build && pnpm build:client && pnpm pack
dsh plugin --profile web add ./dsh-wb-cloud-sync-0.1.0.tgz
# 完全退出桌面版后执行，重启桌面版即生效
```

> 从 GitHub 直装时 pnpm 可能拦截 git 依赖的构建脚本（allowBuilds）；按报错把允许 key 写进 profile 的 `pnpm-workspace.yaml` 再重试。**不想让用户做这项授权，就发布到 npm 或交付 `pnpm pack` 的 tarball**——我们走后者。

## 5. 编码约定

- TypeScript strict；禁止 `any` 逃逸 `ctx` 类型（临时用 `unknown` + 类型守卫）。
- 事件、帧、接口字段全部只读；`SessionEvent` 深冻结后透传，禁止改写 `seq` / `data`。`session/event` 首参是 session 对象，`sessionId` 取 `session.header.id`。
- 命名：`seq` / `sinceSeq` / `clientMsgId` / `deviceId` / `sessionId` 全项目统一，禁止别名。
- 错误一律走 `04` 错误码表，禁止自定义字符串异常冒泡到客户端。
- 日志结构化：`{ ts, level, component, sessionId, deviceId, seq, event, traceId }`，**禁止打印事件正文、token、文件内容**。
- 时间统一 Unix 毫秒；所有网络调用设超时，Relay 侧 10s 无进度即断。

## 7. CI / CD

**CI（push / PR）**：ubuntu + macOS + windows 三平台矩阵 → install → typecheck → build → test → `pnpm pack --dry-run` → `check-plugin.mjs` 加载验证。

**Release（tag `v*`）**：校验 tag 与 `package.json` 版本一致 → 全量测试 → build → `npm publish --access public --provenance` → 构建 Relay 镜像 → 生成 CHANGELOG。

**发版顺序**：协议（`PROTOCOL.md`）→ Relay/CP → Host 插件 → PWA。协议必须先发，避免客户端连上不兼容服务端。

**回滚**：各组件独立版本；Relay/CP 蓝绿；Host 插件 `dsh plugin remove` + 配置备份自动还原；`dsh --profile <name>` 隔离，出问题切回上一 profile。

## 8. 版本锁定与升级流程

1. `pinned-commit.txt` 是唯一真源，CI 校验当前 checkout 与之一致。
2. 上游升级单独开 ADR：先跑全量契约测试 + E2E，列出破坏性变更清单。
3. 升级窗口只在里程碑之后，不在迭代中途。
4. 禁止在运行中的生产 profile 上直接 `pnpm update`。

## 9. 文档规范

- 代码改了 `04` 的字段 → 同 PR 必须改 `04` + `PROTOCOL.md` + CHANGELOG，CI 校验 diff 存在。`PROTOCOL.md` 是 `04` 的**发布副本**，单向同步，不得独立编辑（ADR-009）。
- 每个 ADR 含：状态、决策、理由、后果；不接受"先做再说"的口头决策。
- 用户可见行为变更必须同步 `02` 验收标准与 `10` 部署手册。
