# 07 测试计划与验收标准

> Owner：QA ｜ 版本 v1.0 ｜ 门禁来源：`02` §6

## 1. 测试策略

本项目**不是普通 Web 应用**：核心风险集中在事件序、写入权、崩溃恢复与网络抖动，而非 UI 交互。因此测试投入按「协议与一致性 > 链路 > UI」分配。

| 层 | 投入占比 | 重点 |
|---|---|---|
| 契约 / 一致性 | 35% | seq 连续、幂等、单写者、错误码、未知事件 |
| E2E 链路 | 30% | 手机 → Relay → Host → 同一会话 |
| 混沌 / 恢复 | 20% | 断连、乱序、重试风暴、Host 崩溃 |
| 性能 / 兼容 | 10% | P95、三平台、双端 PWA |
| UI 交互 | 5% | 队列、状态点、产物卡片 |

## 4. 混沌测试方案

`chaos-proxy` 注入以下故障，随机组合、单轮 200 次：

| 故障 | 注入方式 | 观察点 |
|---|---|---|
| 随机断连 | 每 2–15s 断开 WS | 补齐完整率、重连耗时 |
| 乱序 / 重复帧 | 帧队列 shuffle + 重放 | 客户端按 seq 归位、幂等丢弃 |
| 延迟抖动 | 20–1500ms | P95、超时与退避 |
| Host 进程 kill | `SIGKILL` 后重启 | resume `interrupted` 收尾、Route Lease 释放 |
| Relay 重启 | 滚动重启 | 静默重连、令牌保留 |
| CP 不可用 | 停 Postgres | 降级为本地可读索引，写入明确失败而非静默丢 |

**通过标准**：0 丢事件、0 重事件、0 双写、0 文件外泄、所有失败都有明确错误码。

### 4.1 已落地：确定性混沌套件（`p1/relay/test/chaos.test.mjs` · C1–C8）

上表的 `chaos-proxy` 是**计划中的故障注入代理**，尚未实现。当前先用**进程内确定性用例**覆盖其中可在单进程复现的五类故障——不依赖时间随机，跑一次得一结论，因此可以直接进门禁（G10 现场重跑）：

| 用例 | 注入的故障 | 判据 | 覆盖上表哪一行 |
|---|---|---|---|
| C1 | 连上即断，重复 200 次（1/3 顺手带一帧在途） | `sockets` / `pending` / `queue` 三张表归零；抖动后握手、心跳、索引、请求往返仍全通 | 随机断连 |
| C2 | Host 猝死（帧已收走未回，连接即断） | 在途请求 **409 `HOST_OFFLINE` 且 retryable**，耗时 < 超时窗口一半 | Host 进程 kill / 随机断连 |
| C3 | 在线 Host 50 并发 | 每个请求按 `reqId` 拿到**自己**的响应；逆序应答也不串号 | 重试风暴 |
| C4 | 离线设备 50 并发 | 全部 409，耗时 < 2s；**不进 pending、不进降级队列** | 409 防悬挂 |
| C5 | 响应逆序返回 | B 先回 A 后回，各自结果正确 | 乱序帧 |
| C6 | 同一 `reqId` 回两次 | 第二次 `ack.status=rejected`，首次结果不被覆盖，连接不断 | 重复帧 |
| C7 | 事件 0 / 2 / 1 乱序到达 + 重复 seq | 2 被扣住（`advanced=0`），1 到达后按 1、2 补推；重复 seq 判 `DUPLICATE`，游标不回退 | 乱序 / 重复帧 |
| C8 | WS 崩溃 → HTTP 心跳拉回在线 → 重连 | 崩溃瞬间在途请求 409；断连期帧落降级队列，重连注册时转交并跑通；索引按 full 重建不残留 | Relay 重启 / 补发路径 |

**未覆盖（仍待 `chaos-proxy`）**：延迟抖动 20–1500ms、CP 停库降级、跨进程 `SIGKILL` 后的 resume 合成。这三类需要真实进程边界，进程内用例无法伪造。

**C2 是本轮压出来的真缺陷**：修复前 Host 猝死时在途请求要**空等满 10s 超时**才回 504 `NO_PROGRESS`。修复在 `p1/relay/src/server.js`——`pending` 条目记住所在连接，`onClose` 时先回收该连接上的在途请求（409 `HOST_OFFLINE`，可重试）再摘 socket；顺序反了就先丢连接、再没人认领这些请求。

## 5. 性能基准

| 指标 | 目标 | 采集 |
|---|---|---|
| 事件端到端 P95（局域网） | < 300ms | `host/emit` → `client/render` 打点 |
| 事件端到端 P95（跨网） | < 800ms | 同上 |
| 补齐吞吐 | ≥ 500 events/s | 断线补发速率 |
| Relay 单实例并发 WS | ≥ 500 | 压测 |
| 内存 | 长会话 5000 事件无增长 | RSS 采样 |
| 帧大小 | ≤ 64KiB，保序 | 帧日志 |

### 5.1 实测基线（2026-11-10 · `node scripts/bench.mjs`）

运行环境：Windows · 13th Gen i5-13600KF / 20 线程 · Node **v24.22.2**（隔离工具链，与发布基线一致）· Relay 单实例 · **本机回环**。证据：`spike/evidence/perf.json`（含直方图与全部样本统计）。

| 用例 | 指标 | 实测 | 判据 | 结论 |
|---|---|---|---|---|
| B1 帧往返（顺序 500 次） | P50 / P95 / P99 | 0.231 / **0.434** / 0.692 ms | P95 < 300ms | PASS |
| B1b 帧往返 | 失败/串号 | 0 | 0 | PASS |
| B2 帧往返（200 并发） | P95 | **73.0 ms** | P95 < 300ms | PASS |
| B2b 帧往返（200 并发） | 失败/串号 | 0 | 0 | PASS |
| B3 事件端到端（1000 条逐条） | P95 | **28 ms**（P50 20ms） | TC-8.1 P95 < 300ms | PASS |
| B3b 事件端到端 | 丢帧 | 0 / 1000 | 0 | PASS |
| B4 事件端到端（1000 条一次灌入） | P95 | **27 ms** | 同上（最坏情形） | PASS |
| B5 10s 防悬挂 | 最大观测延迟 | 73.0 ms | < 10000ms | PASS |
| B6 单实例并发 WS | 同时挂住连接 | **501**（500 业务 + 1 基准主机） | ≥ 500 | PASS |
| B7 并发连接拆除 | 残留 socket | 0 | 0 | PASS |

两点口径必须一起读，否则会高估或低估：

1. **B2 的 73ms 是单线程串行成本，不是排队**。200 个请求 ÷ 73ms ≈ 0.36ms/个，与 B1 的顺序 0.43ms 同量级，说明没有额外的锁或池化等待。首次实现用 `fetch` 测出 98ms，其中约 25ms 是 undici 客户端取连接排队（当时把客户端池耗尽了），换成显式 `maxSockets=1024` 的 keep-alive agent 后才是服务端真实成本。
2. **这些数不含网络 RTT**。帧延迟 = 手机 HTTP → Relay → 同进程 Host 应答 → 回包，是同机最优情形；TC-8.2 的跨网 P95 < 800ms **尚未测**，需要真实中转链路，不能拿本表外推。
