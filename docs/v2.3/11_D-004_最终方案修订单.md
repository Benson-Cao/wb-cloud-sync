## 0. 为什么再改一次

D-003 选了**甲（App 自研渲染器）**，理由是「PC 插件托管远程 UI 会把样式变成电脑端」。这个判断把「插件托管」等同于「托管官方 Web UI」，是错的。

**插件完全可以托管图一那套手机 UI 的 Web 构建。** 于是乙成立，且同时解掉两个问题：

| 顾虑 | 甲 | 修正乙 |
|---|---|---|
| 手机切电脑端后样式 | 与图一一致（但 UI 要重写） | **与图一一致**（同一份代码） |
| 是否重写 UI | 要，消息流/折叠/轨迹/卡片全实现一遍 | **只写一次，两份投放** |
| DSH 官方升级 | 解析逻辑压在 APK，每次升级要发版 | **解析逻辑压在插件，改插件即可** |
| R-29 渲染器漂移 | 红（16） | **降黄** |

## 1. 最终形态

```
       图一那套手机 UI（同一份 Web 前端源码，ui-bundle）
        ├─ 投放点 A：打包进 APK     → 本机引擎档案（on-device）
        └─ 投放点 B：PC 插件托管    → SSH / Relay 档案
                    /__wbsync/ui/*（prefix 路由，静态资源）

┌─ Android App（薄壳）───────────────────────────────────┐
│ Kotlin 平台层：主机切换器 / 配对 / Keystore / 前台服务    │
│ client-core（纯协议）：DshCarrier 三实现 + DshMux        │
│ WebView：加载 ui-bundle（按当前档案选投放点）            │
│ ❌ 无 Cordis / 无 apply(ctx) / 无 bundle / 无 slots      │
│ ❌ 不自研 Renderer / 不做事件解析                        │
└────────────────────┬──────────────────────────────────┘
     三个 Carrier 只换传输，业务层同一套 watch / prompt
┌────────────────────▼──────────────────────────────────┐
│ PC：DSH + dsh-wb-cloud-sync（**唯一插件**）              │
│  apply(ctx)：事件透传 / 幂等 / Route / 索引上报          │
│  ctx.webServer：/__wbsync/* + /__wbsync/ui/* 托管 UI    │
│  client 半边：桌面设置页 / 配对码                       │
└───────────────────────────────────────────────────────┘
手机 Termux（真源 A）：原版 dsh web，不装我们的包
```

**分工一句话**：样式归 `ui-bundle`，数据归主机，传输归 Carrier，扩展点归 PC 插件。

## 3. 乙方案的两个真坑（必须写进实现）

1. **两份 client 资源不可混用**：PC 的 `dsh.client` 跑在 Electron `file://` + IPC 桥转发 fetch；手机 WebView 是普通 HTTP。`ui-bundle` 里的 fetch 必须相对路径 + 可配置 base，不能假设 `/api` 一定在本域。投放点 B 下由插件把 `/__wbsync/ui/*` 的 API 请求反代到同一 Host 的 `dsh web`。
2. **PC 离线时 WebView B 打不开**：App 必须内置一层极简离线骨架（设备列表、状态点、明确提示「该主机离线」），不能白屏。

## 4. ADR-014（插入 `03` §8，取代 ADR-013 的甲方案部分）

### ADR-014 UI 单一源码、双投放点；传输按 Carrier 抽象
- **状态**：已接受（D-004）
- **决策**：手机界面为一份 `ui-bundle` 源码，打包进 APK（本机档案）与由 PC 插件 prefix 路由托管（SSH/Relay 档案）两个投放点；App 不自研事件解析；`client-core` 以三个 `DshCarrier` 实现承载差异，能力由 carrier 自报。
- **理由**：满足「切到电脑端后手机仍保持图一样式与功能」的产品承诺；UI 只写一次；DSH 上游升级的解析改动落在插件侧而非 APK；避免甲方案的 R-29 红风险与重复渲染实现。
- **取代**：取代 ADR-013 中「App 自研渲染器」条款；ADR-013 的「PC 唯一插件 / 手机不做插件 / Termux 原版 DSH」继续有效。
- **后果**：新增 `/__wbsync/ui/*` 静态契约与 `uiBundleVersion`；CI 校验两端 bundle 哈希一致；App 需处理 PC 离线骨架；`renderContract` 与 Golden Fixture **降级为回归手段**，不再是一致性主保证（主保证是同源 UI）。
- **不推翻**：ADR-007~012 全部继续有效。

### ADR-013 状态修订
> 原「App 自研渲染器」改为「App 内置 `ui-bundle` 的本地投放点」；`RENDERER_VERSION_MISMATCH` 保留但语义改为 UI bundle 版本错配。

## 5. 新增 / 修订契约字段（`04`）

```
# PC 插件本地路由新增
prefix  /__wbsync/ui/*     静态托管 ui-bundle（无业务逻辑）

# 握手响应新增
X-UI-Bundle-Version: <semver>
X-UI-Bundle-Sha256: <hash>     # App 与插件各报一份，CI 与运行时校验

# 新错误码
UI_BUNDLE_MISMATCH   409  App 内置 bundle 与插件托管 bundle 版本不兼容，提示升级 App 或插件

# Carrier 能力接口（client-core 内部契约）
supportsUplink: boolean
allowsEndpoint(endpoint): boolean
call(endpoint, args): RpcOk | RpcError
openLink(opts): DshMuxLink    // item / end / error 帧，cancel(streamId)，onLost
```

`renderContract: 1`、`RENDERER_VERSION_MISMATCH` 保留为兼容字段，但**不再是主保证**。

## 7. 产品承诺（最终文案，覆盖 `02` §5）

> **切换到电脑端后，手机 App 的会话详情保持与手机端一致的样式与功能**：气泡、引用卡、对话/轨迹 tab、底部输入框、轮次步数与上下文占用、产物卡、审批、队列与停止，均以同一份 `ui-bundle` 渲染；消息内容来自该电脑的会话日志，为唯一数据源。
>
> 预期差异仅限：与 PC 桌面端的布局差异、PC 专属设置入口、短暂网络延迟与断线补齐窗口、以及由 carrier 显式声明并提示的链路能力限制。除此之外任何样式或内容差异均为缺陷。
