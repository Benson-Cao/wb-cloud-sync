## 一页纸

我们要做一个**手机端直接用官方界面、电脑端是唯一插件点**的跨端工作台：Android 端在 Termux 里装 Node + **原版** DSH，`dsh web` 起在 `127.0.0.1:3080`，手机成为第二台 DSH 主机；手机不装我们的插件、不写自定义 UI、不写移动皮肤。三种档案（本机 / SSH / Relay）下 WebView **打开的都是同一个官方 `dsh web`**——v0.2.2-rc.1 已原生适配窄屏，因此切到电脑端后界面样式与功能天然一致。三个 `DshCarrier` 只换传输，业务层同一套 `watch / prompt`。

云端控制面从「手机→电脑的唯一通道」降级为**账号级主机注册表 + 跨网中继 + 会话索引**，只存元数据，不存事件正文、不存工作区文件。

**核心设计一句话**：**多个真源、显式选主机、每主机内单写者**。会话跟着「执行位置」走，不跟着账号走。

> 与 v1.0 的根本差异：v1 是「一个会话、多个视图、一个写入者」，手机只是投影；v2 手机是**第二个 Agent**，不是投影。ADR-001 已被 ADR-007 取代。

## 目标 / 非目标

### 目标（v2.0）

- G1 手机 App 提供**主机档案切换器**：本机引擎 / SSH 主机 / Relay 主机，当前执行位置始终可见。
- G2 本机引擎下，Termux 内**原版 DSH** 完整可用：跑会话、模型请求走用户自己的提供方；WebView 直接打开**官方 `dsh web` 窄屏 UI**，**不装插件、不注 slots、不写 UI**。
- G3 远程主机下，手机连电脑 DSH，手机与电脑看到同一份会话（v1 能力完整保留）。
- G4 同账号自动发现所有主机，会话索引按 `hostId` 命名空间汇总，跨主机可见但需连上对应主机才读正文。
- G5 账号级同步设置 / Memory / 自动化定义；产物卡、审批卡以**工具卡**形式随事件下发，任何主机都能渲染。
- G6 任务执行中发消息进队列、共享上下文、不打断；断线按 `seq` 补齐，不丢不重。
- G7 文件与工作区始终留在**产生它的那台主机**，云端零文件落地。

### 非目标（Charter 防蔓延）

- **不做主机间会话/文件/插件迁移**：切换主机 = 切换执行位置，不带走上下文。
- **不做 iOS 本机引擎**：iOS 降级为 PWA 远程视图（只读 + 连电脑），不跑 DSH。
- **不做云端执行 / 云端沙箱**、不把会话正文上云。
- **不做多人实时协作编辑同一会话**、不做 IM 助理渠道（v3 评估）。
- **不改 DSH 内核**：不 fork、不 patch 内核，全部走插件接缝。
- **不做 PRoot 打包 APK**：Termux 方案已足够，避免 ~1GB rootfs 与侧载签名问题（见 ADR-009）。
- **★ 手机侧不交付 dsh 插件、不写 UI**（D-003 + D-005）：无 Cordis / bundle / slots / 插件管理器 / **UI 源码 / 移动皮肤**；App 只保留 `client-core` 与三块 Kotlin 原生页面，Termux 只跑原版 DSH。
- **★ 手机侧不支持第三方插件扩展 UI**（D-003）：PC 侧 `dsh-wb-cloud-sync` 是唯一插件点。

## 术语表（v2 新增项加 ★）

| 术语 | 含义 |
|---|---|
| **DSH / dsh** | DeepSeek Harness，Cordis 内核的开源 Agent 运行框架 |
| **Host / 主机** | 一台能跑 DSH 的执行点；v2 里手机与 PC 都是 Host |
| ★ **本机引擎** | Termux 内 `npx @deepseek-ai/dsh web` 起的手机端 DSH，绑 `127.0.0.1:3080` |
| ★ **主机档案 HostProfile** | App 内显式选择的执行位置：`on-device` / `ssh` / `relay` |
| ★ **hostId** | 主机唯一标识；`SessionIndex` 主键为 `(hostId, sessionId)` |
| ★ **launch token** | `dsh web` 启动时打印的一次性 token，WebView 换 cookie 后访问本地服务 |
| ★ **协议内置卡片** | 随 `SessionEvent` 下发的 `wbsync/card`，`kind` 为封闭枚举，App `CardRegistry` 原生渲染 |
| ★★ **官方原生 UI** | **手机界面 = 官方 `dsh web` 窄屏呈现**；三档案 WebView 都直接寻址它，仓库里无 UI 源码 |
| ★★ **DshCarrier** | `client-core` 的可插拔传输接口，只实现 `call()` + `openLink()`；三个实现 `Local / Ssh / Relay` |
| ★★ **DshMux** | 与传输无关的流复用层：重连、generation、`watch()` 重同步、待处理审批 |
| ★ **能力声明** | `supportsUplink` / `allowsEndpoint` 由 carrier 自报，App 不硬编码档案差异 |
| ★ **client-core** | 纯协议客户端（Carrier×3 + Mux），不依赖 UI 框架、**不解析事件、不给 UI 供数** |
| ★ **原生页面** | App 自有的主机切换器 / 配对页 / PC 离线页（Kotlin 层，非 Web UI 皮肤） |
| ★ **pinned-commit** | 锁 v0.2.2-rc.1 对应 commit；双端一致，漂移即 `COMMIT_DRIFT` |
| **CP** | 云端控制面：账号、主机注册表、会话索引、Cursor |
| **Relay** | 自托管中继：配对、挑战响应、WS 帧透传、反向代理 |
| **SessionEvent** | append-only 事件日志单条记录，含 `type / seq / time / data / ignorable?` |
| **seq** | 会话内连续无间隙序号，= `log.length`，用作补齐游标 |
| **Surface** | 投影成消息的四类：`system/message`、`user/message`、`assistant/message`、`tool/result` |
| **Bundle / Client 半边** | `dsh.bundle` + `dsh.client` 两个 manifest 声明的安装包 |
| **单写者租约** | **每主机内**同一会话只允许一个写句柄 |

## 开工前必须确认的四件事

1. **Spike 优先于编码**：W1 三个 Spike 全过才进 P1 —— ① Termux 装 nodejs → **原版** `dsh web` 起 3080 → launch token 换 cookie → **WebView 加载官方窄屏 UI**；② 手机经 SSH `:3081` / Relay 反代打开同一官方 `dsh web`，窄屏渲染可用；③ 宿主「不打开写句柄即可提交消息」入口可用。详见 `12` S-1.2/1.3/1.4。**基线锁 v0.2.2-rc.1**。
2. **双端锁同一 commit**：`pinned-commit.txt` 同时约束 PC 与 Termux 的 DSH 版本；事件格式版本化，漂移即拒绝索引合并。
3. **环境基线**：PC 侧 Node ≥ 24.9 / pnpm 11；Termux 侧 `pkg install nodejs git`，Node 版本需满足同一 commit 的 engines；`NODE_OPTIONS` 不含 `--no-experimental-strip-types`。
4. **产品预期管理**：首次启动引导必须明说「切换主机不会带走会话和文件」，并在主机切换器上常驻当前执行位置。
