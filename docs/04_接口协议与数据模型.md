## 1. 通用约定

- 传输：HTTPS + WSS，TLS 1.2+；HTTP 接口 `Content-Type: application/json`。
- 所有请求带 `Authorization: Bearer <deviceToken>`（配对接口除外）。
- 所有响应带 `X-Protocol-Version: wbsync/1`。
- 时间统一 Unix 毫秒；ID 用字符串，不用自增整数。
- 幂等键 `clientMsgId` 由客户端生成（UUID v4），**直接映射宿主 `prompt(request).requestId`**；宿主按 `message.source.rpcId` 原生去重（24h 为语义上界，实际以宿主 inbox 生命周期为准）。Host 侧不另建幂等表，见 ADR-008。
- 帧搬运：Relay 按 ≤ 64KiB 帧切分，**帧序即流序**，接收方按序重组；SSE 与二进制 blob 不切语义边界。

### 统一响应包

```jsonc
{ "ok": true,  "data": { }, "protocol": "wbsync/1" }
{ "ok": false, "error": { "code": "HOST_OFFLINE", "message": "...", "retryable": false } }
```

### 错误码表

| code | HTTP | 含义 | 可重试 |
|---|---|---|---|
| `UNAUTHORIZED` | 401 | 令牌缺失/失效/已吊销 | 否（需重新配对） |
| `PAIR_CODE_INVALID` | 400 | 配对码错误/过期/超限 | 否 |
| `CHALLENGE_EXPIRED` | 400 | 挑战超过 60s | 否 |
| `ENDPOINT_NOT_ALLOWED` | 403 | 不在 `allowedEndpoints` 白名单 | 否 |
| `HOST_OFFLINE` | 409 | 目标 Host 未注册到 Relay | 是（稍后） |
| `ROUTE_CONFLICT` | 409 | 会话写句柄归属其他 Host | 否 |
| `SESSION_BUSY` | 409 | 单写者租约被占用 | 是（退避） |
| `DUPLICATE` | 200 | `clientMsgId` 已处理 | 否（视为成功） |
| `NO_PROGRESS` | 504 | 10s 无进度防悬挂触发 | 是 |
| `SESSION_FORMAT_UNSUPPORTED` | 422 | 日志格式版本本构建无法解读 | 否 |
| `UNKNOWN_EVENT_IGNORED` | — | 客户端侧：跳过 `ignorable` 未知事件 | — |

## 2. 数据模型（CP / Postgres）

```sql
-- 账号（OAuth 主体）
Account {
  accountId      text PK,
  provider       text,        -- 'google' | 'github'
  subject        text,        -- OAuth sub
  settings       jsonb,       -- 偏好、Assistant 配置
  memoryRef      text,        -- Memory 存储引用（正文不在本表）
  automations    jsonb,       -- 定时任务定义
  createdAt      bigint
}

-- 设备注册表
Device {
  deviceId       text PK,     -- Host 侧稳定生成，重装不变
  accountId      text FK,
  deviceName     text,        -- 取「关于本机」，改名下次连接同步
  platform       text,        -- 'windows' | 'macos' | 'linux'
  capabilities   jsonb,       -- ['attachments','artifacts','schedule','approval']
  tokenDigest    text,        -- SHA-256(deviceToken)，绝不存明文
  allowMobile    boolean,     -- 「允许移动端连接此设备」开关
  state          text,        -- 'online' | 'offline'
  lastSeenAt     bigint,      -- 心跳 15s，>45s 判离线
  tombstone      boolean      -- 删除/吊销后重启不复活
}

-- 会话索引（不含事件正文）
SessionIndex {
  sessionId      text PK,
  accountId      text FK,
  ownerDeviceId  text FK,     -- 会话创建/执行所在 Host
  workspace      text,        -- 来自 SessionHeader.cwd
  title          text,
  pinned         boolean,
  pinnedOrder    int,
  state          text,        -- 'running' | 'awaiting' | 'completed' | 'stopped' | 'failed' | 'unreadable'
  lastSeq        bigint,      -- 会话内连续 seq 上界
  lastActiveAt   bigint,
  headerRef      jsonb        -- version,parentSession,delegationDepth,agentPreset,isSeeded,origin
}

-- 写句柄租约（硬约束：一会话一写者）
RouteLease {
  sessionId      text PK,
  deviceId       text,
  leaseId        text,
  expiresAt      bigint       -- 心跳续租；过期释放
}

-- 客户端消费位点
Cursor {
  clientId       text,
  sessionId      text,
  sinceSeq       bigint,
  updatedAt      bigint,
  PRIMARY KEY (clientId, sessionId)
}

-- 幂等表（CP 侧：仅跨 Host 路由审计；进程内去重由宿主 requestId 承担，见 ADR-008）
Idempotency {
  scope          text,        -- deviceId
  clientMsgId    text,        -- = 宿主 prompt(request).requestId
  result         jsonb,
  createdAt      bigint,
  PRIMARY KEY (scope, clientMsgId)
}
```

**`state` 映射（r2 新增）**：由 `turn/end.reason` 单向决定 —— `completed | max-tokens → completed`（`max-tokens` 附截断标记）、`aborted → stopped`（远程停止，已完成步骤保留）、`error | interrupted → failed`、`blockaded → awaiting`；日志格式不可解读时 `unreadable`。同一会话同一时刻只上报一种状态，随 `session/index` 增量帧下发，客户端不自行推断。对齐 WorkBuddy 对话级五态（运行中 / 等待输入 / 已完成 / 已停止 / 失败）。

> `SessionHeader` 字段（DSH 侧）：`version / id / createdAt / cwd / parentSession / isSeeded / origin / delegationDepth / agentPreset`。跨设备展示工作空间与会话谱系以它为准，**不要自己猜标题或层级**。

## 3. DSH 事件契约（透传，不改字段）

```ts
type SessionEvent = {
  type: string                   // 实测 32 种，如 'user/message' | 'tool/result' | 'job/registered'
  seq: number                    // 会话内从 0 起连续递增，无间隙，= 事件总数 - 1
  time: number                   // Unix ms
  data: unknown                  // 必须可 JSON 序列化
  surfaceOp?: 'append' | string  // 宿主投影指令（实测 163 条，恒为 'append'）
  sourceEventSeqs?: number[]     // 关联源事件 seq；实测仅出现在 tool/result（73 条）
  ignorable?: true               // 保留字段：实测宿主不下发，客户端不得依赖
}
```

### 事件分类（决定客户端渲染）

| 类别 | 事件 | 客户端处理 |
|---|---|---|
| **Surface（投影成消息）** | `system/message`、`user/message`、`assistant/message`、`tool/result` | 渲染为对话消息 |
| 轮次/步骤 | `turn/start`、`turn/end`、`step/start`、`step/end` | 过程条、状态点 |
| 工具调用 | `tool/call` | 与 `tool/result` 按 `sourceEventSeqs`（`callId` 为辅）配对展示 |
| 仅日志 | `request/header`、`todo/write`、`hook/invoked`、`hook/result`、`request/context`、`session/end-seed` | 不进消息流 |
| 压缩 | `compaction/start`、`compaction/summary`、`compaction/end` | 遮蔽旧节点，视图缩短，**日志原文不变，禁止回写** |
| 恢复 | `turn/end { reason: { kind: 'interrupted' } }` | 由 resume 合成，仅崩溃恢复出现 |
| **其它（默认跳过）** | 实测 20+ 种：`permission/preset`、`sandbox/mode`、`approval/*`、`job/*`、`llm/retry*`、`session/title*`、`workspace/*`、`subagent/*`、`team/*` | 白名单外一律跳过，**不依赖 `ignorable` 标记** |

**宿主实测补充（DSH 0.2.2-rc.1，667 条事件样本）**

- 事件形状三种：基础 504 条；带 `surfaceOp` 90 条；带 `surfaceOp` + `sourceEventSeqs` 73 条。
- **日志中不存在 `assistant/chunk`**：流式分片不落盘，落盘的是最终 `assistant/message`，无需 chunk 折叠。
- **`ignorable` 字段 0 次**；`sourceEventSeqs` 只出现在 `tool/result` 上，用于关联 `tool/call`，不是 chunk 折叠字段。
- `session.v4.jsonl.zstd` 是**多帧 zstd 拼接**：每批追加一个独立帧；只解第一帧会误判成「会话只有一条 header」。离线回放工具必须逐帧解压。
- `session/event` 订阅回调首参是 **session 对象**，`sessionId` 取 `session.header.id`。

`turn/end` 原因枚举：`completed / aborted / blockaded / error / max-tokens / interrupted`。任一步骤触顶时整轮按 `max-tokens` 计（截断事实优先于 completed）。

> `SessionHeader` 实测字段：`type / version / id / createdAt / cwd / isSeeded / delegationDepth / agentPreset`；v1.0 注释中的 `parentSession` / `origin` 在样本中未出现，按**可选字段**处理，跨设备谱系展示须做缺失兜底。

## 4. CP REST 接口

```
GET  /api/me                         → Account + settings
GET  /api/me/devices                 → Device[]（含 state / 状态点 / deviceName）
GET  /api/sessions?deviceId=&pinned= → SessionIndex[]（含 lastSeq / state）
GET  /api/approvals?deviceId=         → 待审批清单（r5；断线期间的靠这条补）
POST /api/sessions                   → 在指定在线 Host 新建会话/工作空间
PATCH /api/sessions/:id              → 置顶 / 调序（仅 PC 端可写，手机 403）
DELETE /api/sessions/:id             → 移除工作空间（同步到手机）
POST /api/devices/:id/revoke         → 吊销令牌 + 断开在线手机
GET  /api/artifacts?sessionId=       → 产物元数据 + 临时下载票
```

**约束**：
- `POST /api/sessions` 在目标设备离线时返回 `HOST_OFFLINE`，手机端入口置灰。
- 手机对 `pinned / pinnedOrder` 只读；置顶与调序必须由 PC 端发起。
- CP 不提供任何"读取消息正文"接口。

## 5. Relay 接口

```
POST /pair                        配对码 → challenge → HMAC → deviceToken
GET  /manifest.webmanifest        无鉴权静态（PWA 必需）
GET  /admin                       管理台（--admin-token）
WS   /ws/host                     Host 注册长连
WS   /d/<deviceId>/events/*       事件流（WS 帧透传）
ANY  /d/<deviceId>/session/*      HTTP 反向代理到 Host
ANY  /d/<deviceId>/fileUploads/*  附件上行（r3 新增；HTTP 反向代理到 Host）
ANY  /d/<deviceId>/$events/*      审批 / 提问通道（r5：$events/result 应答审批，先答先得）
```

### 5.1 配对时序

```
1. PC 设置页「生成配对码」
   → CP: { code: "482913", deviceId, ttl: 600s, rateLimit: 5/min per device+IP }

2. 手机 POST /pair { code }
   ← 200 { challenge: "<nonce>", expiresIn: 60, deviceId }

3. 手机计算 sig = HMAC-SHA256(pairSecret, challenge)
   POST /pair/verify { challenge, sig, clientId }
   ← 200 { deviceToken, protocol: "wbsync/1", relayUrl }

4. Relay 落 tokenDigest = SHA-256(deviceToken)
   该 deviceId 原活跃令牌立即作废（单活跃令牌）
   手机持令牌静默重连
```

> 配对码只是下载引导之外的**一次性信任建立**，不是登录凭证；二维码本身不参与配对。

### 5.2 Host 注册帧

```jsonc
// Host → Relay (WS /ws/host)
{ "t": "host/register", "deviceId": "...", "protocol": "wbsync/1",
  "caps": ["attachments","artifacts","schedule","approval"],
  "hostToken": "<HOST_TOKEN>" }

{ "t": "host/sessions", "rows": [ /* SessionIndex[] 全量 */ ] }
{ "t": "host/heartbeat", "ts": 1730000000000 }        // 15s
```

### 5.3 帧透传规则

```jsonc
// 上行（Host → 手机）
{ "t": "session/event", "sessionId": "...", "ev": SessionEvent }
{ "t": "session/index", "rows": [ /* 增量 SessionIndex */ ] }
{ "t": "$events", "kind": "approval|question|plan_review", "payload": {...} }

// 下行（手机 → Host）
{ "t": "session/prompt",  "sessionId": "...", "text": "...", "clientMsgId": "uuid" }
{ "t": "session/cancel",  "sessionId": "..." }
{ "t": "session/follow",  "sessionId": "...", "sinceSeq": 123 }
{ "t": "$events/result",  "eventId": "...", "answer": {...} }
{ "t": "ack", "ref": "clientMsgId", "status": "accepted|duplicate|rejected" }
```

**保序**：Relay 不重排帧；同一 `sessionId` 的 `seq` 必须单调递增到达。若检测到乱序，客户端缓存并等待缺口填补，超时按 `NO_PROGRESS` 上报。

**帧大小（2026-11-11 真机修订）**：`session/follow` 的响应按 **≤48 KiB/页字节预算**裁，不是按固定 500 条。真机取证：某会话 74 条事件就有 454 KiB（平均 6.1 KiB/条，正文里带整段文件内容），按旧版 500 条一页推算约 **3 MiB** —— Relay WS 收到超过 `MAX_PAYLOAD`(1 MiB) 的帧会以 **1009 `frame too large` 直接断连**，在途补齐请求无人应答，只能熬到 10s 后 504 `NO_PROGRESS`。症状看似「补齐卡住」，根因是帧撑爆连接。

- 裁页用 UTF-8 实算字节数，不按字符数猜（中文正文会低估 3 倍）。
- 至少返回一条：单条就超预算时若一条都不给，`sinceSeq` 永远推不动，客户端会无限重试。
- 单条超过 768 KiB 硬上限时**不发帧**，改回明确 `FRAME_TOO_LARGE` 413。宁可给一个能诊断的错误码，也不要静默断连。
- 响应新增可选字段 `bytes`（本页字节数）、`oversized`（单条硬塞过去）。
- 客户端补齐翻页上限从 8 提到 200，并加「`hasMore=true` 但游标没推进就立刻停」的兜底（防 200 次空转打 Relay）。

#### 单帧上限与超大事件降级（r7 新增）

真机实测 874 条事件：单条最大 **421 KiB**、p99 **97 KiB**、p50 0.2 KiB，其中 21 条超过 64 KiB——「帧 ≤64KiB」是设计愿望，不是事实。

| 位置 | 上限 | 行为 |
|---|---|---|
| Relay 解析 WS 帧 | `maxFrameBytes` 默认 **8 MiB** | 超过即 1009 关闭；旧版写死 1 MiB，长回复很容易顶破 |
| Host 转发单条事件 | 软上限 **1 MiB** | 超过则**降级**：保留 `seq` / `type` / `time` 等顶层元数据，`data` 换成 `{ truncated: true, reason: 'EVENT_TOO_LARGE', bytes, head }` |
| Relay 事件缓冲 | `eventBufferBytes` 默认 **32 MiB** | 按条数（1000）**与字节**双重裁剪，只裁已广播的旧条目 |

**为什么降级而不是丢弃**：丢掉一条事件会让 `seq` 出现空洞，客户端判缺口 → 触发补齐 → 补齐又被同一条撑爆，形成死循环。降级保留 `seq`，游标照常推进，手机上显示「该事件正文 N KiB 超过单帧上限未转发」，完整内容在电脑上。

**为什么上限可配而不是写死**：1 MiB 是零依赖 WS 解析器的内存安全边界，不该由协议常量定死；真机数据已到 421 KiB，留 2 倍余量即可。配置下限被夹在 1 KiB，误配不会把所有帧都拒掉。

**关闭通知**：服务端主动关连接（1009 超限、吊销、停机）也必须触发一次 `onClose`。此前 `conn.close()` 先把 `open` 置 false，socket 的 `close` 事件直接 return，设备一直留在 CP 的「在线」窗口里，手机请求被投进降级队列干等 10s 才 504。

### 5.4 正文可见性边界（r2 新增，信任边界澄清）

**事实**：`session/event` 帧的 `ev.data` 就是会话正文。Relay 终止 TLS 后按 ≤64KiB 帧透传，因此 **Relay 进程可见事件帧明文**；CP 不接收该帧。

| 维度 | v1 保证 | 不保证 |
|---|---|---|
| 落盘（at-rest） | CP 无正文表、Relay 不写盘；事件流只在内存中转发 | — |
| 传输（in-transit） | Host↔Relay、Relay↔手机全链路 TLS 1.2+ | **不保证对 Relay 运维的机密性**（可见明文正文） |
| 工作区文件 | 根本不经过 Relay / CP | — |

- **统一口径**：项目内所有「会话正文不上云」解释为 **「零正文落盘、零正文进入 CP」**，不解释为「零正文经过 Relay」。`02` NFR-4、`08` §6、`07` TC-7.6 的出网审计目标据此收敛为「0 字节工作区文件 + 0 条正文写入持久化层」。
- **依赖**：正文机密性依赖 **自托管 Relay + 运维可信 + 主机访问控制**，不依赖密码学隔离；部署方须限制 Relay 主机登录、关闭核心转储与调试抓包，见 `10` §6。
- **升级路径**：若要求「即使 Relay 被攻破也拿不到正文」，须引入 Host↔手机端到端加密载荷（`enc` 字段 + 配对期密钥交换），属**不兼容变更**，升 `wbsync/2` 并单独立 ADR；v1 明确不做（ADR-010）。
- 与 WorkBuddy 官方「安全中继通道加密 + 为在移动端展示而收集对话内容与任务记录」的差异见 `WORKBUDDY-REFERENCE.md` §3.1。

### 5.5 审批转发（r5 新增）

宿主契约（`app.asar` 实测，非本项目自创）：

```ts
type ApprovalOutcome = 'allowed-once' | 'rejected' | 'cancelled' | 'unavailable'
type ApprovalPolicy  = 'ask' | 'never'
interface ApprovalRequest { agent; toolName: string; callId?; reason?; displayReason?; signal? }
ctx.on('approval/request', (request, next) => Promise<ApprovalOutcome>)   // 瀑布
```

**分工：Host 判、Relay 存、手机拉。**

| 方向 | 载体 | 说明 |
|---|---|---|
| Host → Relay | WS 帧 `$events/request` | `{ approvalId, sessionId, toolName, callId, reason, expiresAt }` |
| Relay → 手机 | WS 帧 `approval/request` | 推给**该设备的所有**手机订阅连接（审批是设备级的，与看哪个会话无关） |
| 手机 → Relay（拉） | `GET /api/approvals?deviceId=` | 返回未过期条目；**断线期间错过的靠这条补**，推送只负责更快 |
| 手机 → Relay | `POST /d/<deviceId>/$events/result` | `{ approvalId, outcome: 'allowed-once' \| 'rejected' }` |
| Relay → Host | `http/request` 帧（`endpoint: '$events/result'`） | 走既有下行分派，Host 不新增通道 |
| Host → Relay | WS 帧 `$events/resolved` | 先答/超时/abort 时撤卡，`by: 'phone' \| 'host' \| 'timeout' \| 'expired' \| 'shutdown'` |

**三条不变量**：

1. **先答先得**。手机第二次点、第二台手机点、或手机点晚了，一律 409 `APPROVAL_GONE`；桌面端先答时宿主 `signal` 会 abort，Host 随即发 `$events/resolved` 让手机撤卡。两端都不许改写已定结果。
2. **手机不在线或超时 → `next()`**，把这一单交还宿主自己的弹窗。**不返回 `unavailable`**：宿主的语义里 `unavailable` 等于「无人可审批」，会直接拒掉这次工具调用；而手机没答上只是「没来得及」，桌面端还有机会。
3. **`unavailable` 只由宿主产生**，手机侧只允许 `allowed-once` / `rejected`（`cancelled` 由宿主或超时决定）。手机传别的串一律 400。

`approvalId` 由 Host 生成（UUID），Relay 只做键；`expiresAt` 也由 Host 给——**超时的决定权在决定者手里**，Relay 只做惰性清理。

### 5.6 产物索引（r6 新增，元数据边界）

宿主实测：会话日志里有一种显式交付事件

```jsonc
{ "type": "deliverables/presented", "seq": 3, "data": {
    "turn": 1, "callId": "call-1",
    "files": [{ "path": "out/a.pdf", "description": "成品" }]
}}
```

`POST /d/<deviceId>/session/artifacts`（请求体 `{sessionId}`）走**既有** `session/*` 下行通道，Host 用 `sessionPersistence.open(id,'read')` 只读分页扫一遍日志，返回：

| 字段 | 含义 |
|---|---|
| `rows[]` | `{ seq, turn, callId, index, path, name, description }`，按 `seq` 排序 |
| `count` / `scanned` | 行数 / 扫过的事件数 |
| `truncated` | 达到页数或行数上限时**如实报 true**，不谎称扫全了 |

为什么不让手机直接从事件流里攒卡片：Relay 的事件缓冲在内存里（capacity 1000），长会话会把早期交付事件裁掉；手机晚连、Relay 重启、缓冲被裁时卡片就空了。会话日志是 append-only 真源，问 Host 才能补齐——**和 `session/follow` 走的是同一条补齐逻辑**。

**边界（ADR-010 / §5.4）**：只过元数据，**文件字节一个都不许进 Relay / CP**。卡片能做的只有「看到有什么」和「复制路径」，打开文件归桌面端自己的文件动作。导出 PDF/DOCX、临时下载票尚未实现；要做必须先立 ADR 处理「工作区文件是否允许经过 Relay」这个信任边界变化，不能顺手把字节塞进 `rows[]`。

畸形事件（缺 `turn` / `callId` / `files`、路径空白、描述非字符串）一律跳过，**不猜路径、不编文件名**；同名文件在两个 `seq` 各留一行，不按路径合并。

**真机观察（2026-11-11，DSH 重启后实测）**：只认显式交付事件是有代价的。抽查一个 874 条事件的真实会话（`胎教Agent`）：`deliverables/presented` **0 条**，但 `tool/result` 正文里确实出现过生成的文件路径；`workspace/changes` 只有 `{turn:5}`，**不带文件列表**（宿主 UI 要另查 Host 的 change summary 路由，并从成功的写文件工具调用里解析参数才凑得出交付卡片）。所以 `session/artifacts` 对这类会话如实返回 `rows:[]`，不是解析失败——真机事件字段确认为 `{type, seq, time, data, sourceEventSeqs, surfaceOp}`，与解析器假设一致。

**暂不从工具调用里猜路径**：宿主自己都要求「malformed calls contribute nothing」「reads/deletes 不计入」，我们没有那套参数校验与工具白名单，硬凑只会把中间产物、被删文件、读过的文件全当成「交付」。等宿主暴露 change summary 或产物清单接口再接，见 `05` W8 遗留项。

### 5.7 首屏窗口与反向补读（r8 新增）

手机打开会话时**不再全量补齐**。真机 874 条事件按 48 KiB/页要走数十到上百个往返，首屏要等好几秒；而用户 99% 的情况只想看最近发生了什么。

- **窗口按字节定，不按条数定**：先 `POST /session/backfill { beforeSeq: lastSeq + 1, limit: 200 }`，由 Host 按 **48 KiB 字节预算**裁出「最近一页」，拿到 `toSeq` 后再 `follow(sessionId, { sinceSeq: toSeq })` 接实时流。客户端不再猜窗口起点。
  - 为什么不是固定 50 条：50 条 × 40 KB 的工具结果 = **2 MB**，50 条 × 200 B 的碎片 = **10 KB**，同一数字在两种会话里完全不是一回事。
  - **条数下限 8**：若最新几条都是几十 KB 的巨型事件，纯按预算只剩 1~2 条，一屏都不满、上下文也没了；不足 8 条时允许超预算，但**不超过 4× 预算**（防 8 条 × 1 MiB 把帧撑爆）。
  - 索引里没有 `lastSeq`（老数据）时才退回 `follow(-1)` 全量引导补齐。
- **反向补读**：`POST /d/<deviceId>/session/backfill`，请求 `{ sessionId, beforeSeq, limit }`，返回紧邻窗口前面的那一段：

| 字段 | 含义 |
|---|---|
| `events[]` | `seq < beforeSeq` 的最后 `limit` 条（按 `seq` 升序） |
| `fromSeq` / `toSeq` | 本段的起止 seq |
| `hasMoreEarlier` | 最早一条 `seq > 0` 即前面还有；界面据此决定要不要继续显示「加载更早」 |
| `bytes` | 本段字节数（同样受 48 KiB 预算约束） |

**预算从后往前砍**：超预算时丢的是更早的那些，紧邻窗口的最新几条必须留下——否则用户点十次「加载更早」都看不到紧接着的那几条。

**兼容旧 Host**：旧插件不认 `session/backfill`（白名单内但没实现，回 403 `ENDPOINT_NOT_ALLOWED`）。客户端退回「`follow` 从 `beforeSeq-limit-1` 取一页再筛掉 `>= beforeSeq`」，按钮不会变砖；响应里带 `via: 'follow'` 标明这是降级路径。

**为什么不用 `follow` 硬拉**：`follow` 只能从某点**向后**走，补“更早”会把后面的全部重发一遍；要凑够一屏历史得翻好几页。反向读一次请求就够。

## 6. Host 本地接口（`ctx.webServer` 具名路由）

| kind | path | 用途 |
|---|---|---|
| exact | `/__wbsync/pair` | 生成/展示配对码 |
| exact | `/__wbsync/status` | 连接状态、设备信息、版本号 |
| exact | `/__wbsync/config` | 读写 relayUrl / hostToken / autoConnect |
| prefix | `/__wbsync/static/` | client 半边静态资源 |
| exact | `/__wbsync/artifacts/:id` | 产物临时下载票换流 |

- `register()` 返回 disposer，**必须**交 `ctx.effect()`；插件卸载时路由自动撤回。
- exact/prefix 匹配顺序固定：先全表 exact → 最长前缀 → 回退处理器。**重复注册同 kind+path 会抛异常**，视为配置错误。
- 回退席位全局唯一，本项目不注册回退。
- 桌面 Electron 经 `file://` + IPC 桥转发 fetch，不经过本地 HTTP server；client 半边需适配该链路。

## 7. 权限白名单

```yaml
allowedEndpoints:
  - 'session/*'
  - 'fileUploads/*'   # r3：附件上行；只经 Relay 内存中转，不落盘、不缓存、不进事件流
  - '$events/*'
  # 'session/artifacts'（r6）不需要单独登记：它落在 'session/*' 内，且只回元数据
```
默认拒绝其余一切；高危操作（文件写入、执行命令、读屏）默认全关闭，逐项显式授权后才开放。

**`fileUploads/*` 的边界（r3）**：
- 请求体为 `{ sessionId, data: base64(标准编码), name? }`，`data` 上限由 Relay 的 `maxBodyBytes`（1 MiB）约束，即原始文件约 ≤ 750 KiB。
- 文件内容只在 Relay 进程内**内存中转**（手机 → 自托管 Relay → 本机 Host），**不落盘、不缓存、不写入事件流、不进入 CP**；ADR-010 的「CP/Relay 零正文落盘」口径不变。
- Host 侧调用宿主 `fileUploads`，返回 `receiptId`；`receiptId` 只在接收 Agent 作用域内有效，必须与**同一 session** 的 `session/prompt` 一起使用，不得跨会话复用。
- 文件是否真正进入模型上下文由宿主的 admission 规则决定；本协议不承诺任何媒体类型，类型校验与大小限制归宿主。

**端点归一化（r4）**：白名单比对的是**解码后**的端点，且 `xxx/*` 只放行**单段**（`session/prompt`）。
`session/..%2Fadmin%2Frevoke`、`session/prompt/extra`、`session/%2e%2e/admin` 一律 403 `ENDPOINT_NOT_ALLOWED`。
理由：前缀匹配 `startsWith('session/')` 会把「看起来以 session/ 开头」的穿越串放行给 Host 二次解码，
白名单形同虚设。对应渗透用例 S6。

## 7.1 `/host/*` 的凭据（r4）

`/host/*` 是 Host 侧的管理面，**每个端点独立校验**（它们是独立 HTTP 请求，彼此没有会话关联，
只在注册处查一次等于其余端点裸奔）。配置了 `hostToken` 时必须带，三种载体任选其一：

| 载体 | 形式 | 用在哪 |
|---|---|---|
| 请求头 | `Authorization: Bearer <HOST_TOKEN>` | 推荐；`/host/poll` 等 GET 也用它 |
| 请求体 | `{ "hostToken": "<HOST_TOKEN>" }` | POST 的兼容写法 |
| 查询串 | `?hostToken=<HOST_TOKEN>` | 旧 Host 的降级轮询 |

未配置 `hostToken` 视为**明确的单机开发模式**（`run.mjs` 启动会打警告），不静默放行。

| 端点 | 缺凭据的后果（未加此闸时实测） | 现在 |
|---|---|---|
| `GET /host/poll` | 同网段任何人可读到手机待发的提示词正文与 `reqId` | 401 |
| `POST /host/respond` | 拿到 `reqId` 后可直接伪造 Host 回复，改写手机看到的结果 | 401 |
| `POST /host/sessions` | 可向任意设备的会话列表投毒（伪造行、删行） | 401 |
| `POST /host/heartbeat` | 可把离线设备伪装成在线，让手机持续投递直到全部超时 | 401 |

对应渗透用例 S11–S14。WS 侧 `/ws/host` 的 `host/register` 早已校验同一令牌；
另外升级请求本身不带凭据，因此未注册连接有 `registerTimeoutMs`（默认 10s）硬截止（S10）。

## 9. 版本与兼容

- 协议版本放在每次握手的 `protocol` 字段；不兼容变更升 `wbsync/2`，Relay 同时兼容 1/2 两个版本至少 90 天。
- 新增事件类型一律由客户端按白名单默认跳过；**不得依赖服务端 `ignorable` 标记**（实测宿主不下发，见 §3）。
- 新增字段必须可选 + 有默认值；删除字段走 90 天弃用期。
- 字段类型以锁定 DSH commit 为准；升级 DSH 前跑全量契约测试（见 `07`）。
- **r1（2026-11-07）**：按 W1 Spike 实测澄清事件契约、幂等映射与 Idempotency 归属；仅新增可选字段与说明，无删除/改名，兼容 `wbsync/1` 现有客户端；依据 ADR-007~009（待会签）。
- **r2（2026-11-10）**：`SessionIndex.state` 扩充 `stopped` / `failed` 两个枚举值并给出 `turn/end.reason` 映射；新增 §5.4 正文可见性边界；修正「新增事件依赖 `ignorable`」的过时表述。无删除、无改名，兼容 `wbsync/1` 现有客户端；依据 WorkBuddy 对标复核与 ADR-010（待会签）。
- **r3（2026-11-10）**：新增 `fileUploads/*` 附件上行端点（`POST /d/<deviceId>/fileUploads/upload`）与 §7 的白名单项、安全边界（Relay 内存中转、receipt 限 Agent 作用域）；`session/prompt` 的 `content` 允许 `{type:'file',receiptId}`（宿主 schema 原本已支持，本次仅明确手机侧用法）。无删除、无改名，兼容 `wbsync/1` 现有客户端；发起人裁定采纳（四方会签已取消）。
- **r8（2026-11-11）**：新增 §5.7 首屏窗口与反向补读。手机打开会话默认只看**最近一页**（Host 按 48 KiB 字节预算裁，最少 8 条、最多 200 条），更早的按需调新增端点 `POST /session/backfill`（`{sessionId, beforeSeq, limit}` → `{events, fromSeq, toSeq, hasMoreEarlier, bytes}`）。端点落在既有 `session/*` 白名单内，不新增帧；旧 Host 回 403 时客户端退回 `follow` 取一页，不破坏兼容。
- **r7（2026-11-11）**：新增 §5.3 传输上限与超大事件降级。WS 单帧上限可配（默认 8 MiB）、Host 侧 1 MiB 软上限触发**事件降级**（保留 `seq`，正文摘成 `head`）、Relay 事件缓冲加 32 MiB 字节预算；修正「帧 ≤64KiB」与实测（最大 421 KiB）不符的表述。新增字段均为可选（`data.truncated` / `data.reason` / `data.bytes` / `data.head`），旧客户端只会看到一条普通事件，不破坏兼容。
- **r6（2026-11-10）**：新增 `session/artifacts` 下行端点（§5.6）。位于既有 `session/*` 白名单内，**不新增帧、不新增字段、不改白名单规则**；Host 只读扫会话日志中的 `deliverables/presented` 事件，返回文件元数据。显式规定「文件字节不经 Relay」，导出/下载票未实现，需先立 ADR 再动这个信任边界。兼容 `wbsync/1` 现有客户端（旧端不调用该端点即无感）。
- **r5（2026-11-10）**：新增 §5.5 审批转发。宿主 `approval/request` 瀑布经 Host 插件转成 `$events/request` 上行帧，Relay 存看板并广播 `approval/request` 给该设备所有手机，手机用 `POST /d/<id>/$events/result` 应答，补拉走 `GET /api/approvals`。新增帧类型均为**新增可选**，旧客户端按白名单跳过、不参与审批即无感；不升主版本。依据宿主实测契约（`ApprovalOutcome` 四值）与渗透用例 S1–S16 的口径。
- **r4（2026-11-10）**：安全收紧，两处**行为变更**（字段与端点名均未变，但原先能通的做法现在会被拒）：① §7 白名单改为「解码后比对 + `xxx/*` 只放行单段」，穿越与多重编码串从「放行给 Host 解码」改为 403；② 新增 §7.1，`/host/*` 每个端点独立校验 `hostToken`（此前只有 `/host/register` 校验），未配置时仍为单机开发模式。另：WS 未注册连接加 `registerTimeoutMs`（默认 10s）截止；请求体必须是 JSON 对象。依据渗透用例 S6 / S8 / S10 / S11–S14。
