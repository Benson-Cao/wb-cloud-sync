## 1. 通用约定

- 传输：HTTPS + WSS，TLS 1.2+；HTTP 接口 `Content-Type: application/json`。
- 所有请求带 `Authorization: Bearer <deviceToken>`（配对接口除外）。
- 所有响应带 `X-Protocol-Version: wbsync/2.3`（响应体的 `protocol` 字段同值）。
- 时间统一 Unix 毫秒；ID 用字符串，不用自增整数。
- 幂等键 `clientMsgId` 由客户端生成（UUID v4），**直接映射宿主 `prompt(request).requestId`**；宿主按 `message.source.rpcId` 原生去重（24h 为语义上界，实际以宿主 inbox 生命周期为准）。Host 侧不另建幂等表，见 ADR-008。
- 帧搬运：Relay 按 ≤ 64KiB 帧切分，**帧序即流序**，接收方按序重组；SSE 与二进制 blob 不切语义边界。

### 统一响应包

```jsonc
{ "ok": true,  "data": { }, "protocol": "wbsync/1" }
{ "ok": false, "error": { "code": "HOST_OFFLINE", "message": "...", "retryable": false } }
```

### 错误码表

| code | HTTP | 含义 | 可重试 |
|---|---|---|---|
| `UNAUTHORIZED` | 401 | 令牌缺失/失效/已吊销 | 否（需重新配对） |
| `PAIR_CODE_INVALID` | 400 | 配对码错误/过期/超限 | 否 |
| `CHALLENGE_EXPIRED` | 400 | 挑战超过 60s | 否 |
| `ENDPOINT_NOT_ALLOWED` | 403 | 不在 `allowedEndpoints` 白名单 | 否 |
| `HOST_OFFLINE` | 409 | 目标 Host 未注册到 Relay | 是（稍后） |
| **`HOST_MISMATCH`** | **409** | **两种不相符场景（r19 起双语义）：① 注册协商——注册帧声明的协议版本与 Relay 不符（r16 落地；WS 侧为 close 1008）；② 主机切换——手机令牌有效但请求的 hostId ≠ 令牌绑定主机（S-6.9 BE-CP 落地：切换器重绑后旧 hostId 请求的专属信号，WS 订阅侧为握手 409）** | 否 |
| **`CONFIRM_REQUIRED`** | **400** | **切换主机未带显式 `confirmNoMigration:true`（布尔；字符串 "true" 不算）——「不带走会话/文件/插件」的服务端强制点（r19 落地）** | 否（补确认后重发） |
| **`COMMIT_DRIFT`** | **409** | **主机 DSH commit 与 Relay 配置的 pinned 基线不一致，拒绝注册即索引不合并（r16 落地；未配 pinned 时仅记录不拦截）** | 否 |
| `CLIENT_LIMIT` | 409 | 该 Host 已绑定的手机达到上限（r9，默认 8 台） | 否（先在管理台收回一台） |
| **`DEVICE_KEY_MISMATCH`** | **409** | **r24 / S-8.5：手机携带的 `devicePubKey` 与该设备已钉住的指纹不一致，配对被阻断（不提供「提醒后继续」）；已签发的旧令牌仍有效** | 否（由管理员收回设备后重新配对） |
| `ROUTE_CONFLICT` | 409 | 会话写句柄归属其他 Host | 否 |
| `SESSION_BUSY` | 409 | 单写者租约被占用 | 是（退避） |
| `DUPLICATE` | 200 | `clientMsgId` 已处理 | 否（视为成功） |
| `NO_PROGRESS` | 504 | 10s 无进度防悬挂触发 | 是 |
| `SESSION_FORMAT_UNSUPPORTED` | 422 | 日志格式版本本构建无法解读 | 否 |
| **`ENGINE_SAFE_MODE`** | **503** | **主机自报引擎处于安全模式：`/d/<hostId>/*` 一律 503，不把请求投给跑不了的引擎（r16 落地；声明驱动，重新声明 running 即恢复）** | 是（修配置后恢复） |
| `UNKNOWN_EVENT_IGNORED` | — | 客户端侧：跳过 `ignorable` 未知事件 | — |

## 2. 数据模型（CP / Postgres）

```sql
-- 账号（OAuth 主体）
Account {
  accountId      text PK,
  provider       text,        -- 'google' | 'github'
  subject        text,        -- OAuth sub
  settings       jsonb,       -- 偏好、Assistant 配置
  memoryRef      text,        -- Memory 存储引用（正文不在本表）
  automations    jsonb,       -- 定时任务定义
  createdAt      bigint
}

-- 设备注册表（Host 与手机各占一行，见 role）
Device {
  deviceId       text PK,     -- Host：Host 侧稳定生成，重装不变；手机：手机侧生成，重配沿用
  role           text,        -- 'host' | 'phone'（r9）
  boundHostId    text FK,     -- 仅 role='phone'：它配对的那台 Host（r9）
  accountId      text FK,
  deviceName     text,        -- 取「关于本机」；手机侧取配对时自报的名字（仅展示）
  platform       text,        -- 'windows' | 'macos' | 'linux' | 'mobile'
  hostId         text,        -- v2.3（r15）：主机标识正式名；本轮值 = deviceId（命名迁移第一步）
  dshCommit      text,        -- v2.3（r16）：注册帧声明的 DSH 基线；与 pinned 不符即 COMMIT_DRIFT
  engineState    text,        -- v2.3（r16）：主机自报引擎状态；'safe-mode' 时 /d/* 全量 503
  capabilities   jsonb,       -- ['attachments','artifacts','schedule','approval']
  tokenDigest    text,        -- SHA-256(deviceToken)，绝不存明文；一台设备一枚活跃令牌
  allowMobile    boolean,     -- 「允许移动端连接此设备」开关
  state          text,        -- 'online' | 'offline'
  lastSeenAt     bigint,      -- 心跳 15s，>45s 判离线
  tombstone      boolean      -- 删除/吊销后重启不复活
}

-- 会话索引（不含事件正文）
-- 键 = (ownerDeviceId, sessionId)（r17 单机实现按复合键隔离；Postgres 版 PK = (hostId, sessionId)，
--     同名 sessionId 在两台主机下可共存，v2.3 §2）
SessionIndex {
  sessionId      text,
  accountId      text FK,
  ownerDeviceId  text FK,     -- 会话创建/执行所在 Host（Postgres 版改列名 hostId）
  PRIMARY KEY (ownerDeviceId, sessionId),   -- r17：复合主键（原为 sessionId 单列 PK）
  workspace      text,        -- 来自 SessionHeader.cwd
  title          text,
  pinned         boolean,
  pinnedOrder    int,
  archived       boolean,     -- r12：软移除标记；缺省 false（旧 Host/客户端）
  state          text,        -- 'running' | 'awaiting' | 'completed' | 'stopped' | 'failed' | 'unreadable'
  lastSeq        bigint,      -- 会话内连续 seq 上界
  lastActiveAt   bigint,
  headerRef      jsonb        -- version,parentSession,delegationDepth,agentPreset,isSeeded,origin
}

-- 写句柄租约（硬约束：一会话一写者）
RouteLease {
  sessionId      text PK,
  deviceId       text,
  leaseId        text,
  expiresAt      bigint       -- 心跳续租；过期释放
}

-- 客户端消费位点
-- 键 = (clientId, hostId, sessionId)（r17；位点按主机隔离，同一手机在两台主机各记各的）
Cursor {
  clientId       text,
  hostId         text,
  sessionId      text,
  sinceSeq       bigint,
  updatedAt      bigint,
  PRIMARY KEY (clientId, hostId, sessionId)
}

-- 幂等表（CP 侧：仅跨 Host 路由审计；进程内去重由宿主 requestId 承担，见 ADR-008）
-- 键 = (ownerDeviceId, clientMsgId)（r17 起带 host 维度；Postgres 版 PK = (hostId, clientMsgId)）
Idempotency {
  scope          text,        -- deviceId
  clientMsgId    text,        -- = 宿主 prompt(request).requestId
  result         jsonb,
  createdAt      bigint,
  PRIMARY KEY (scope, clientMsgId)
}
```

**手机为什么要独立成行（r9）**：r8 之前令牌直接写在这台 Host 的 `tokenDigest` 上，等于一台电脑只有一枚活跃令牌 —— 第二台手机一配对，第一台立刻 401；而「丢了其中一台」也没法只收回那一台。r9 让手机成为 `role='phone'` 的独立设备行：

- URL 里的 `hostId` 仍然是**目标 Host**（`/d/<hostId>/…`，r16 起路径段语义改名；值兼容 `deviceId`，旧客户端 URL 不用改；`/api/*?hostId=` 查询参数 r17 起为正式名，`deviceId=` 继续接受），令牌却属于某台手机；服务端按「该 Host 名下是否有这枚令牌」鉴权。
- 一台 Host 默认最多绑 **8** 台手机（`maxPhonesPerHost`），超限配对返回 `CLIENT_LIMIT`。
- 同一台手机重新配对（`phoneId` 不变）只**轮换它自己**那枚令牌，「重配即作废旧令牌」这条按手机成立。
- 吊销可以逐台做（按手机 `deviceId`）；吊销 Host 则连坐名下全部手机。
- **墓碑不是黑名单**：被收回的手机拿新的配对码回来，允许重新配对（令牌在收回时已清空，重配只发新令牌）。Host 侧仍拒绝墓碑复活——`host/register` 不带任何人工动作，两者不对称是刻意的。
- 手机的消费位点用它的 `deviceId` 作 `Cursor.clientId`，两台手机各自记账。

**单机期 CP 落盘（P2 前置）**：CP 的 Postgres 实现之前，单机版把**设备表（含令牌摘要）与会话索引**写进一个 JSON 文件（默认 `~/.wbsync/cp.json`，可用 `WBSYNC_CP_FILE` 改），重启后手机不必重新配对。两条刻意的不存：

- **租约**（TTL 30s）不存——重启后本就该全部失效，存下来只会让「会话被谁占着」的假象多活 30 秒；
- **消费位点**不存——`sinceSeq` 由客户端唯一权威（#5b），服务端那份只是可观测性快照。

加载时一律按**离线**起身，并清理三类行：墓碑超过 30 天的设备、归属设备已不存在的会话与手机。文件只含摘要与索引元数据，**没有正文**，ADR-010 的边界不变。

**`state` 映射（r2 新增）**：由 `turn/end.reason` 单向决定 —— `completed | max-tokens → completed`（`max-tokens` 附截断标记）、`aborted → stopped`（远程停止，已完成步骤保留）、`error | interrupted → failed`、`blockaded → awaiting`；日志格式不可解读时 `unreadable`。同一会话同一时刻只上报一种状态，随 `session/index` 增量帧下发，客户端不自行推断。对齐 WorkBuddy 对话级五态（运行中 / 等待输入 / 已完成 / 已停止 / 失败）。

> `SessionHeader` 字段（DSH 侧）：`version / id / createdAt / cwd / parentSession / isSeeded / origin / delegationDepth / agentPreset`。跨设备展示工作空间与会话谱系以它为准，**不要自己猜标题或层级**。

## 3. DSH 事件契约（透传，不改字段）

```ts
type SessionEvent = {
  type: string                   // 实测 32 种，如 'user/message' | 'tool/result' | 'job/registered'
  seq: number                    // 会话内从 0 起连续递增，无间隙，= 事件总数 - 1
  time: number                   // Unix ms
  data: unknown                  // 必须可 JSON 序列化
  surfaceOp?: 'append' | string  // 宿主投影指令（实测 163 条，恒为 'append'）
  sourceEventSeqs?: number[]     // 关联源事件 seq；实测仅出现在 tool/result（73 条）
  ignorable?: true               // 保留字段：实测宿主不下发，客户端不得依赖
}
```

### 事件分类（决定客户端渲染）

| 类别 | 事件 | 客户端处理 |
|---|---|---|
| **Surface（投影成消息）** | `system/message`、`user/message`、`assistant/message`、`tool/result` | 渲染为对话消息 |
| 轮次/步骤 | `turn/start`、`turn/end`、`step/start`、`step/end` | 过程条、状态点 |
| 工具调用 | `tool/call` | 与 `tool/result` 按 `sourceEventSeqs`（`callId` 为辅）配对展示 |
| 仅日志 | `request/header`、`todo/write`、`hook/invoked`、`hook/result`、`request/context`、`session/end-seed` | 不进消息流 |
| 压缩 | `compaction/start`、`compaction/summary`、`compaction/end` | 遮蔽旧节点，视图缩短，**日志原文不变，禁止回写** |
| 恢复 | `turn/end { reason: { kind: 'interrupted' } }` | 由 resume 合成，仅崩溃恢复出现 |
| **其它（默认跳过）** | 实测 20+ 种：`permission/preset`、`sandbox/mode`、`approval/*`、`job/*`、`llm/retry*`、`session/title*`、`workspace/*`、`subagent/*`、`team/*` | 白名单外一律跳过，**不依赖 `ignorable` 标记** |

**宿主实测补充（DSH 0.2.2-rc.1，667 条事件样本）**

- 事件形状三种：基础 504 条；带 `surfaceOp` 90 条；带 `surfaceOp` + `sourceEventSeqs` 73 条。
- **日志中不存在 `assistant/chunk`**：流式分片不落盘，落盘的是最终 `assistant/message`，无需 chunk 折叠。
- **`ignorable` 字段 0 次**；`sourceEventSeqs` 只出现在 `tool/result` 上，用于关联 `tool/call`，不是 chunk 折叠字段。
- `session.v4.jsonl.zstd` 是**多帧 zstd 拼接**：每批追加一个独立帧；只解第一帧会误判成「会话只有一条 header」。离线回放工具必须逐帧解压。
- `session/event` 订阅回调首参是 **session 对象**，`sessionId` 取 `session.header.id`。

`turn/end` 原因枚举：`completed / aborted / blockaded / error / max-tokens / interrupted`。任一步骤触顶时整轮按 `max-tokens` 计（截断事实优先于 completed）。

> `SessionHeader` 实测字段：`type / version / id / createdAt / cwd / isSeeded / delegationDepth / agentPreset`；v1.0 注释中的 `parentSession` / `origin` 在样本中未出现，按**可选字段**处理，跨设备谱系展示须做缺失兜底。

### 3.1 协议内置卡片 `wbsync/card`（r23 / S-8.3）

> 依据 v2.3 04 §4 / §4.1、02 FR-3.3、03 ADR-011/015、07 TC-1.12 / 5.11 / 5.12。
> **Relay 保持纯帧透传**（P5 / ADR-010 / §5.4）：不解析事件正文、不改日志原文、
> 不动 `seq`。校验落在发送端契约层与接收端归一化层，两端共用同一份实现
> （`p1/pwa/src/cards.js` 是唯一实现，`p1/client-core/src/cards.js` 只做再导出——
> PWA 静态根只有 `pwa/public` 与 `pwa/src`，实现放在客户端侧才不会在浏览器 404）。

| 项 | 规定 |
|---|---|
| 卡片类型 | `t: "wbsync/card"`；随 `SessionEvent` 的 `data` 下发，落进会话日志 |
| 字段 | `cardId`（非空、≤128 字符）、`kind`、`view`（普通对象）、可选 `actions[]`（≤16 项，每项 `id` / `label` 为字符串） |
| `kind` | **封闭枚举** `artifact / approval / metric / table`，卡片 schema `wbsync.card/1`。新增 kind 必须升 schema 并走协议变更，客户端不得私加类型 |
| 限额 | 单卡 ≤ 8 KiB、面板视图 ≤ 32 KiB（UTF-8 字节，按 JSON 序列化计）、合并 ≤ 4 Hz、效果窗口 3s |
| 违规 | 清单校验失败**只丢弃该条目**并累计问题数；连续 5 次违规整体降级为 web 版本，`reset()`（重启引擎 / 重新启用）后恢复 |
| 未知 kind | 客户端显示**灰色占位**（`placeholder: true` + 保留 `rawKind`），不静默丢弃、不降级、不影响其余 UI（TC-5.12） |
| 渲染 | 客户端只渲染 JSON 数据，不执行任何插件代码；违规正文不交给渲染器 |
| 跨链路 | 本机 / SSH / Relay 三个 carrier 只搬运同一份 `ev`；live 与 replay 走同一投递出口，归一化结果与链路无关（TC-5.11） |

错误码（`validateCard` / `createCardGuard` 的 `code`）：`BAD_SHAPE` / `BAD_CARD_ID` /
`BAD_KIND` / `BAD_VIEW` / `BAD_ACTIONS` / `CARD_TOO_LARGE` / `VIEW_TOO_LARGE` /
`RATE_LIMITED` / `DEGRADED`。未知但非空的 `kind` **不算错误**（返回 `knownKind: false`），
由归一化层出灰色占位。

> 接收端识别三种形态：`data.t === "wbsync/card"`、事件体 `t` / `type` 声明，
> 以及 `t` 写坏但仍带 `cardId` / `kind` / `view` 中至少两项的疑似卡片（交给校验器
> 记 `BAD_SHAPE`，不允许伪装成普通事件静默溜过）。PWA 侧 `onCard` 回调拿到的
> 是归一化模型；`snapshot().cards` 只暴露问题数 / 降级标记，不暴露正文。

## 4. CP REST 接口

```
GET  /api/me                         → Account + settings
GET  /api/me/devices                 → Device[]（含 state / 状态点 / deviceName）
GET  /api/hosts                      → HostProfile[]（P2 新增；r20：手机令牌看全部非墓碑主机（可切清单）+ `bound` 标记、不收 phones[]；adminToken 看全部含 phones[]）
                                      行 = { hostId, deviceId, kind:'relay', name, platform, dshCommit,
                                             engineState, online, state, lastSeenAt, sessionCount,
                                             bound, phones[]（admin 视角）}
POST /api/hosts/select               → 主机切换器（r19，S-6.9 BE-CP）
                                      请求 = { hostId, confirmNoMigration: true }（切换时 confirm 必须显式 true）
```

**约束**：
- **(hostId, sessionId) 命名空间隔离（r17）**：会话索引、写句柄租约、消费位点的键全部带 host 维度——同名 sessionId 在两台主机下可共存，互不覆盖（S-2.2 验收；R-22 串会话的数据层防线）。`/api/*` 查询/正文参数以 `hostId=` 为正式名，`deviceId=` 继续接受（同一台主机同一枚值，旧客户端零改动）；响应对象补 `hostId` 字段（只增不删）。
- **可切主机清单（r20，S-6.9 数据面）**：`GET /api/hosts` 手机令牌返回**全部非墓碑主机**（v2.3 文档包 04 §7 `/api/me/hosts` 的 HostProfile[] 多台语义）——切换器 UI 选目标主机与 S-6.8 离线页设备清单的共同数据源；当前绑定行 `bound:true`、其余 `bound:false`；手机视角**不收 `phones[]`**（其它主机的手机清单属管理信息）；admin 视角 `bound:null` + `phones[]`。手机令牌的有效性仍以绑定关系为准（无绑定的令牌 / 坏令牌 → 401，不会因清单放宽而放行其它主机数据）。
- **主机切换协议（r19，S-6.9 BE-CP）**：① 切换判定只信**令牌反查**的当前绑定，请求体里伪造 `from` 不参与判定；② 实际切换（目标 ≠ 当前绑定）必须显式 `confirmNoMigration: true`（缺省/假值 → 400 `CONFIRM_REQUIRED`，绑定不被改动）；③ 切换即重绑（CP `rebindPhone`：目标存在且非墓碑、目标名下手机未达 `CLIENT_LIMIT`、同主机 no-op；令牌不变、绑定变）；④ 切换即刻清理该手机在旧/新两台主机的反代会话票并断开旧主机事件订阅长连；⑤ **离线目标也允许切**（切过去看离线页，S-6.8），响应如实报 `online:false`；⑥ 客户端收到响应后清空当前会话视图、按新 `hostId` 重拉 `SessionIndex` 重建链路；此后任何携带旧 `hostId` 的请求 → 409 `HOST_MISMATCH`（§1 错误码表）；⑦ `dshCommit` 与客户端 pin 的基线不一致时**索引不合并、只提示升级**（客户端判定；服务端注册协商的 `COMMIT_DRIFT` 拦截在 r16，select 响应如实回 `dshCommit` 供客户端比对）。
- **切换器客户端半边（r22，S-6.9 FE）**：`p1/client-core/src/host-switch.js` 的 `createHostSwitcher` 是控制面协议层——`listHosts()` 取可切清单（`bound` 行决定当前执行位置）、`selectHost({ hostId, confirmNoMigration })` 发切换。**客户端本地先拦**未显式 `=== true` 的确认（TC-4.2，不发网络请求；字符串 `'true'` / `1` 一律不算），同主机 no-op 例外。切换成功后 `viewEpoch++` 并经 `onHostChanged` 要求 App 壳执行 `clearView` / `resetCookieJar` / `rebuildIndex`（12 号手册 S-6.9 的坑：独立 cookie jar 是挡住 R-22 串会话的关键，本模块不碰 WebView、不代管 carrier）；`snapshot()` 供顶部执行位置常驻（TC-4.6）。`canMergeIndex(hostId)` 是索引合并闸门（TC-4.3 / TC-1.11）：只允许合并当前主机的索引，`drift` 期间一律拒绝。PWA 沿用 r9「多令牌档案切换」世界观，**不接服务端切换器**——绑定被换时按 r20 的 409 `HOST_MISMATCH` 兜底提示切档案。
- **写操作客户端落地（r22，命名迁移第四步）**：`p1/client-core/src/session-writes.js` 的 `createSessionWrites` 与 PWA 客户端一律走 `PATCH|DELETE /api/sessions/:hostId/:id`，`hostId` 只在路径段（不再塞 body/query）；切换后由 `setHostId()` 或列表响应的权威 `hostId` 同步路径段，否则携带旧 `hostId` 的请求按 r19 判 409 `HOST_MISMATCH`。`DELETE` 仍是归档别名（软移除，不真删）；`pinned` / `archived` / `title` 一次只给一个（与服务端 400 `INVALID_JSON` 同款约束，客户端先拦）。服务端旧单段形态兼容期保留不变。
- `POST /api/sessions` 在目标设备离线时返回 `HOST_OFFLINE`，手机端入口置灰。
- 手机可置顶 / 取消置顶（`PATCH { pinned }`，r11）；**排序**（`pinnedOrder`）仍由 Host 权威（最近置顶在前），手机不改序——两端各自维护顺序只会打架。**调序**仍仅 PC 可写。
- **手机不真删会话**（r12）：「移除工作空间」= 归档，只把行标成 `archived=true`、从默认列表隐藏；落盘日志一行不动。`DELETE /api/sessions/:id` 是归档别名（强制 `archived=true`），恢复走 `PATCH { archived:false }`。真删仅 PC 侧可做。
- CP 不提供任何"读取消息正文"接口。

## 5. Relay 接口

```
POST /pair                        配对码 → challenge → HMAC → deviceToken
GET  /manifest.webmanifest        无鉴权静态（PWA 必需）
GET  /admin                       管理台（--admin-token）；列出 Host 及其名下手机
POST /admin/revoke                吊销一台设备（r9：Host 连坐其名下手机）
POST /admin/revoke-client         单独收回一台手机（r9；Host 与其它手机不受影响）
WS   /ws/host                     Host 注册长连（r16：注册协商拦截）
WS   /d/<hostId>/events/*         事件流（WS 帧透传）
ANY  /d/<hostId>/session/*        HTTP 反向代理到 Host
ANY  /d/<hostId>/fileUploads/*    附件上行（r3 新增；HTTP 反向代理到 Host）
ANY  /d/<hostId>/$events/*        审批 / 提问通道（r5：$events/result 应答审批，先答先得）
ANY  /d/<hostId>/ui(/**)          ★ 官方 dsh web HTTP 反代（r18，S-6.7 方案 A；?pt= 换会话票）
WS   /d/<hostId>/ui/**            ★ 官方 dsh web WS mux socket 级透传（r18；/api/remote.mux 等）
```

> 上表路径段一律指**目标 Host 的 `hostId`**（r16 语义改名，值兼容 `deviceId`）；手机自己的身份不出现于路径（r9）。
>
> **r16 注册协商**：`/ws/host` 注册帧声明 `protocol` 与 Relay 不符 → close `1008 HOST_MISMATCH: …`；`dshCommit` 与 Relay 配置的 `pinnedDshCommit` 不符 → close `1008 COMMIT_DRIFT: …`。两者都发生在落库之前，被拒帧不留下设备行。HTTP 降级通道 `POST /host/register` 同口径回 409。**只拒绝「明确声明且不符」**：未声明字段的旧客户端照常注册。
>
> **r16 ENGINE_SAFE_MODE**：注册帧声明 `engineState: 'safe-mode'` 的主机在线，但 `/d/<hostId>/*` 全量 503（HTTP 回错误体；WS 订阅回裸 503），重新声明 `running` 即恢复——声明驱动、后到优先。

### 5.1 配对时序

```
1. PC 设置页「生成配对码」
   → CP: { code: "482913", deviceId, ttl: 600s, rateLimit: 5/min per device+IP }

2. 手机 POST /pair { code }
   ← 200 { challenge: "<nonce>", expiresIn: 60, deviceId }

3. 手机计算 sig = HMAC-SHA256(pairSecret, challenge)
   POST /pair/verify { challenge, sig, phoneId?, clientName?, devicePubKey? }
   ← 200 { deviceToken, deviceId: <本机 phoneId>, hostDeviceId, protocol, relayUrl }

4. Relay 为这台手机写一行 Device（role='phone', boundHostId=<Host>），
   令牌摘要落在这行上（只存 SHA-256）：
   - phoneId 相同 = 同一台手机重配 → 覆盖它自己那枚令牌，旧令牌立即失效；
   - phoneId 缺省 / 未见过 → 新的一台手机（受 maxPhonesPerHost 约束，超限 CLIENT_LIMIT）；
   - 其它手机的令牌不受影响。
   手机持令牌静默重连，URL 用 hostDeviceId。
```

> `relayUrl` 回的是**这次请求所用的地址**（未配置 `publicBaseUrl` 时按 Host 头拼，反代后取 `X-Forwarded-Proto`）：手机必须拿到一个它连得上的地址，绝不能是 `127.0.0.1`——手机上的 127.0.0.1 是手机自己，会直接 `ERR_CONNECTION_REFUSED`。

> 配对码只是下载引导之外的**一次性信任建立**，不是登录凭证；二维码本身不参与配对。

**r24 / S-8.5 设备公钥 pin（B3 TOFU）**：`devicePubKey` 是手机设备公钥的
SHA-256 指纹（64 位 hex，大小写归一），由 App 壳计算后随 `/pair/verify` 提交。

| 场景 | 行为 |
|---|---|
| 首次配对带合法指纹 | 钉住到该手机行（`Device.devicePubKey`），随 CP 落盘，`hydrate` 恢复 |
| 同一手机带**相同**指纹续配 | 放行，正常轮换令牌 |
| 同一手机带**不同**指纹 | 409 `DEVICE_KEY_MISMATCH`，**阻断**；不改钉住值、不轮换令牌，旧令牌仍有效 |
| 不带 / 格式非法 | 视为未携带，放行且不改钉住值（旧客户端零影响，也不给指纹探测留缝） |
| 管理员 `POST /admin/revoke-client` | 令牌摘要与钉住指纹一起清空、断在线连接、作废 UI 会话票；重新接纳时可钉新指纹 |

> 指纹变更必须阻断而不是「提醒后继续」（12 手册 S-8.5 的坑）。SSH 档案的主机指纹
> 守卫在 `client-core` 的 `SshCarrier`（`SSH_FINGERPRINT_MISMATCH`，r21），与这里的
> **设备**公钥 pin 是两条独立链路：一条防中间人，一条防设备身份被顶替。

### 5.2 Host 注册帧

```jsonc
// Host → Relay (WS /ws/host)
{ "t": "host/register", "deviceId": "...", "hostId": "...", // v2.3：主机标识正式名（本轮值 = deviceId，命名迁移第一步）
  "protocol": "wbsync/2.3",
  "dshCommit": "66491b0…",                                // v2.3（r16）：可选；参与 COMMIT_DRIFT 判定
  "engineState": "running",                                // v2.3（r16）：可选；'safe-mode' 时 /d/* 全量 503
  "deviceName": "工作台-PC", "platform": "win32",          // r10：可选，仅供手机端显示
  "caps": ["attachments","artifacts","schedule","approval"],
  "hostToken": "<HOST_TOKEN>" }

{ "t": "host/sessions", "rows": [ /* SessionIndex[] 全量 */ ] }
{ "t": "host/heartbeat", "ts": 1730000000000 }        // 15s
```

> `hostId` 是 **v2.3（r15）新增的主机标识正式名称**：本轮为命名迁移第一步，Host 发的值等于 `deviceId`，Relay 原样存进 `Device`（限长 64、去空白）并回 `host/registered`；缺省（旧 Host）回落 `deviceId`。`hostId` 参与设备归属判定，与 `deviceId` 等值。
>
> `deviceName` / `platform` 是**可选展示字段**：Relay 去空白、限长（60 / 20）后存进 `Device`，经 `GET /api/sessions` 的 `host` 回给手机（r10）。它们**不参与任何判定**——鉴权、在线、归属都不看这两个字段。缺省（r9 及更早的 Host）照常注册，`host.name` 为 `null`。
>
> `dshCommit` / `engineState` 是 **v2.3（r16）新增的声明字段**：都参与判定，但都遵循「**声明且不符才拒绝**」——`dshCommit` 只在 Relay 配置了 `pinnedDshCommit` 时启用强制校验（未配置时只落库展示）；`engineState` 缺省（旧 Host）按 `running` 对待。声明值去空白限长（64 / 32）后存进 `Device`，未声明保留上次声明值（sticky）；重注册声明新值即覆盖（修配置后无需人工干预即可走出 safe-mode）。
>
> `uiUrl` 是 **v2.3（r18）新增的可选字段（S-6.7 方案 A）**：官方 dsh web 的带令牌回环 URL，由插件按宿主官方先例（desktop-host / web-runtime 同款公式）派生：`ctx.inject(["connection","webServer"])` 就绪回调里取 `connection.authenticatedUrl(\`${webServer.protocol}//127.0.0.1:${webServer.port}/\`)`；派生失败（旧版宿主 / 服务未就绪 / 非回环 / 缺 token）就不发字段，服务晚于首次注册就绪时插件弹一次连接重注册。Relay 三关校验（http(s) / 回环主机 / 带 token）后**只存内存**——不进 CP、不落盘、不进日志、不进任何响应体；重新注册缺席即清旧值（令牌已随重启轮换）。`/__wbsync/status` 只回 `uiAvailable` 布尔（该路由免鉴权公开，绝不回 URL 本体）；`GET /api/hosts` 行同理只报 `uiAvailable`。

### 5.3 帧透传规则

```jsonc
// 上行（Host → 手机）
{ "t": "session/event", "sessionId": "...", "ev": SessionEvent }
{ "t": "session/index", "rows": [ /* 增量 SessionIndex */ ] }
{ "t": "$events", "kind": "approval|question|plan_review", "payload": {...} }

// 下行（手机 → Host）
{ "t": "session/prompt",  "sessionId": "...", "text": "...", "clientMsgId": "uuid" }
{ "t": "session/cancel",  "sessionId": "..." }
{ "t": "session/pin",     "sessionId": "...", "pinned": true }        // r11
{ "t": "session/archive", "sessionId": "...", "archived": true }     // r12
{ "t": "session/artifact-ticket", "sessionId": "...", "path": "out/a.md" }         // r13
{ "t": "session/artifact-ticket", "sessionId": "...", "path": "out/a.docx", "format": "pdf" }  // r14：同一帧，转换后回 PDF
{ "t": "session/follow",  "sessionId": "...", "sinceSeq": 123 }
{ "t": "$events/result",  "eventId": "...", "answer": {...} }
{ "t": "ack", "ref": "clientMsgId", "status": "accepted|duplicate|rejected" }
```

**保序**：Relay 不重排帧；同一 `sessionId` 的 `seq` 必须单调递增到达。若检测到乱序，客户端缓存并等待缺口填补，超时按 `NO_PROGRESS` 上报。

**帧大小（2026-11-11 真机修订）**：`session/follow` 的响应按 **≤48 KiB/页字节预算**裁，不是按固定 500 条。真机取证：某会话 74 条事件就有 454 KiB（平均 6.1 KiB/条，正文里带整段文件内容），按旧版 500 条一页推算约 **3 MiB** —— Relay WS 收到超过 `MAX_PAYLOAD`(1 MiB) 的帧会以 **1009 `frame too large` 直接断连**，在途补齐请求无人应答，只能熬到 10s 后 504 `NO_PROGRESS`。症状看似「补齐卡住」，根因是帧撑爆连接。

- 裁页用 UTF-8 实算字节数，不按字符数猜（中文正文会低估 3 倍）。
- 至少返回一条：单条就超预算时若一条都不给，`sinceSeq` 永远推不动，客户端会无限重试。
- 单条超过 768 KiB 硬上限时**不发帧**，改回明确 `FRAME_TOO_LARGE` 413。宁可给一个能诊断的错误码，也不要静默断连。
- 响应新增可选字段 `bytes`（本页字节数）、`oversized`（单条硬塞过去）。
- 客户端补齐翻页上限从 8 提到 200，并加「`hasMore=true` 但游标没推进就立刻停」的兜底（防 200 次空转打 Relay）。

#### 单帧上限与超大事件降级（r7 新增）

真机实测 874 条事件：单条最大 **421 KiB**、p99 **97 KiB**、p50 0.2 KiB，其中 21 条超过 64 KiB——「帧 ≤64KiB」是设计愿望，不是事实。

| 位置 | 上限 | 行为 |
|---|---|---|
| Relay 解析 WS 帧 | `maxFrameBytes` 默认 **8 MiB** | 超过即 1009 关闭；旧版写死 1 MiB，长回复很容易顶破 |
| Host 转发单条事件 | 软上限 **1 MiB** | 超过则**降级**：保留 `seq` / `type` / `time` 等顶层元数据，`data` 换成 `{ truncated: true, reason: 'EVENT_TOO_LARGE', bytes, head }` |
| Relay 事件缓冲 | `eventBufferBytes` 默认 **32 MiB** | 按条数（1000）**与字节**双重裁剪，只裁已广播的旧条目 |

**为什么降级而不是丢弃**：丢掉一条事件会让 `seq` 出现空洞，客户端判缺口 → 触发补齐 → 补齐又被同一条撑爆，形成死循环。降级保留 `seq`，游标照常推进，手机上显示「该事件正文 N KiB 超过单帧上限未转发」，完整内容在电脑上。

**为什么上限可配而不是写死**：1 MiB 是零依赖 WS 解析器的内存安全边界，不该由协议常量定死；真机数据已到 421 KiB，留 2 倍余量即可。配置下限被夹在 1 KiB，误配不会把所有帧都拒掉。

**关闭通知**：服务端主动关连接（1009 超限、吊销、停机）也必须触发一次 `onClose`。此前 `conn.close()` 先把 `open` 置 false，socket 的 `close` 事件直接 return，设备一直留在 CP 的「在线」窗口里，手机请求被投进降级队列干等 10s 才 504。

### 5.4 正文可见性边界（r2 新增，信任边界澄清）

**事实**：`session/event` 帧的 `ev.data` 就是会话正文。Relay 终止 TLS 后按 ≤64KiB 帧透传，因此 **Relay 进程可见事件帧明文**；CP 不接收该帧。

| 维度 | v1 保证 | 不保证 |
|---|---|---|
| 落盘（at-rest） | CP 无正文表（单机期落一个元数据文件：设备 + 令牌**摘要** + 会话索引）；Relay 不写盘；事件流只在内存中转发 | — |
| 传输（in-transit） | Host↔Relay、Relay↔手机全链路 TLS 1.2+ | **不保证对 Relay 运维的机密性**（可见明文正文） |
| 工作区文件 | 根本不经过 Relay / CP | — |

- **统一口径**：项目内所有「会话正文不上云」解释为 **「零正文落盘、零正文进入 CP」**，不解释为「零正文经过 Relay」。`02` NFR-4、`08` §6、`07` TC-7.6 的出网审计目标据此收敛为「0 字节工作区文件 + 0 条正文写入持久化层」。
- **依赖**：正文机密性依赖 **自托管 Relay + 运维可信 + 主机访问控制**，不依赖密码学隔离；部署方须限制 Relay 主机登录、关闭核心转储与调试抓包，见 `10` §6。
- **升级路径**：若要求「即使 Relay 被攻破也拿不到正文」，须引入 Host↔手机端到端加密载荷（`enc` 字段 + 配对期密钥交换），属**不兼容变更**，升 `wbsync/2` 并单独立 ADR；v1 明确不做（ADR-010）。
- 与 WorkBuddy 官方「安全中继通道加密 + 为在移动端展示而收集对话内容与任务记录」的差异见 `WORKBUDDY-REFERENCE.md` §3.1。

### 5.5 审批转发（r5 新增）

宿主契约（`app.asar` 实测，非本项目自创）：

```ts
type ApprovalOutcome = 'allowed-once' | 'rejected' | 'cancelled' | 'unavailable'
type ApprovalPolicy  = 'ask' | 'never'
interface ApprovalRequest { agent; toolName: string; callId?; reason?; displayReason?; signal? }
ctx.on('approval/request', (request, next) => Promise<ApprovalOutcome>)   // 瀑布
```

**分工：Host 判、Relay 存、手机拉。**

| 方向 | 载体 | 说明 |
|---|---|---|
| Host → Relay | WS 帧 `$events/request` | `{ approvalId, sessionId, toolName, callId, reason, expiresAt }` |
| Relay → 手机 | WS 帧 `approval/request` | 推给**该设备的所有**手机订阅连接（审批是设备级的，与看哪个会话无关） |
| 手机 → Relay（拉） | `GET /api/approvals?deviceId=` | 返回未过期条目；**断线期间错过的靠这条补**，推送只负责更快 |
| 手机 → Relay | `POST /d/<deviceId>/$events/result` | `{ approvalId, outcome: 'allowed-once' \| 'rejected' }` |
| Relay → Host | `http/request` 帧（`endpoint: '$events/result'`） | 走既有下行分派，Host 不新增通道 |
| Host → Relay | WS 帧 `$events/resolved` | 先答/超时/abort 时撤卡，`by: 'phone' \| 'host' \| 'timeout' \| 'expired' \| 'shutdown'` |

**三条不变量**：

1. **先答先得**。手机第二次点、第二台手机点、或手机点晚了，一律 409 `APPROVAL_GONE`；桌面端先答时宿主 `signal` 会 abort，Host 随即发 `$events/resolved` 让手机撤卡。两端都不许改写已定结果。
2. **手机不在线或超时 → `next()`**，把这一单交还宿主自己的弹窗。**不返回 `unavailable`**：宿主的语义里 `unavailable` 等于「无人可审批」，会直接拒掉这次工具调用；而手机没答上只是「没来得及」，桌面端还有机会。
3. **`unavailable` 只由宿主产生**，手机侧只允许 `allowed-once` / `rejected`（`cancelled` 由宿主或超时决定）。手机传别的串一律 400。

`approvalId` 由 Host 生成（UUID），Relay 只做键；`expiresAt` 也由 Host 给——**超时的决定权在决定者手里**，Relay 只做惰性清理。

### 5.6 产物索引（r6 新增，元数据边界）

宿主实测：会话日志里有一种显式交付事件

```jsonc
{ "type": "deliverables/presented", "seq": 3, "data": {
    "turn": 1, "callId": "call-1",
    "files": [{ "path": "out/a.pdf", "description": "成品" }]
}}
```

`POST /d/<deviceId>/session/artifacts`（请求体 `{sessionId}`）走**既有** `session/*` 下行通道，Host 用 `sessionPersistence.open(id,'read')` 只读分页扫一遍日志，返回：

| 字段 | 含义 |
|---|---|
| `rows[]` | `{ seq, turn, callId, index, path, name, description }`，按 `seq` 排序 |
| `count` / `scanned` | 行数 / 扫过的事件数 |
| `truncated` | 达到页数或行数上限时**如实报 true**，不谎称扫全了 |

为什么不让手机直接从事件流里攒卡片：Relay 的事件缓冲在内存里（capacity 1000），长会话会把早期交付事件裁掉；手机晚连、Relay 重启、缓冲被裁时卡片就空了。会话日志是 append-only 真源，问 Host 才能补齐——**和 `session/follow` 走的是同一条补齐逻辑**。

**边界（r6 → r13 按 ADR-011 收窄）**：`rows[]` 永远只有元数据，**文件字节绝不出现在索引里**。r13 起允许用户**显式点「下载」**时，把单个已呈现文件经 Relay **内存中转**给手机：
- `POST /api/artifacts/ticket { sessionId, path }` → `session/artifact-ticket` 下行帧。Host 校验「路径在该会话 `deliverables/presented` 清单里 + 解析后仍在工作区内 + 体积 ≤512 KiB」，通过后只在帧里回 `bytes(base64)`；Relay 把字节留在内存，生成 128bit `ticketId`（60s TTL、单次使用、绑定手机令牌摘要），**手机响应只含 `{ticketId,name,mime,size,expiresIn}`**。
- `GET /api/artifacts/download/:ticketId` → 校验票据与手机令牌，删票后流式回字节（`Content-Disposition: attachment`）。字节不落盘、不缓存、不进事件流、不进 CP。
- **自动同步仍是 0 字节**：出网审计的「0 字节工作区文件」判据收窄为**自动路径**，显式导出单独记审计行（ticketId / 路径哈希 / 字节数 / 时间，**不含正文**）。
- **不伪造格式**：MD/文本/已有 PDF 原样下载。**PDF 转换（r14）只做 Office → PDF**：同一张票据加可选 `format:"pdf"`，Host 交宿主 `officeToPdf.render(scope, path)` 转换后仍回同一个 `bytes` 字段，手机响应多一个 `convertedFrom`。
- **转换的边界**：宿主源码白名单只有 `doc/docx/xls/xlsx/ppt/pptx` 六种，名单外（含 **MD → PDF**）明确 409 `CAPABILITY_UNAVAILABLE`，绝不硬转；转换输入由宿主按自己的 `maxInputBytes` 从磁盘读（**不经我们预读**，否则几 MB 的 Office 文件会先被 512 KiB 上限卡死），只有**输出 PDF** 受 512 KiB 与票据约束；转换失败如实回 `CONVERT_FAILED`，不拿源文件顶替。
- 完整决策与后果见 `03` ADR-011。

畸形事件（缺 `turn` / `callId` / `files`、路径空白、描述非字符串）一律跳过，**不猜路径、不编文件名**；同名文件在两个 `seq` 各留一行，不按路径合并。

**真机观察（2026-11-11，DSH 重启后实测）**：只认显式交付事件是有代价的。抽查一个 874 条事件的真实会话（`胎教Agent`）：`deliverables/presented` **0 条**，但 `tool/result` 正文里确实出现过生成的文件路径；`workspace/changes` 只有 `{turn:5}`，**不带文件列表**（宿主 UI 要另查 Host 的 change summary 路由，并从成功的写文件工具调用里解析参数才凑得出交付卡片）。所以 `session/artifacts` 对这类会话如实返回 `rows:[]`，不是解析失败——真机事件字段确认为 `{type, seq, time, data, sourceEventSeqs, surfaceOp}`，与解析器假设一致。

**暂不从工具调用里猜路径**：宿主自己都要求「malformed calls contribute nothing」「reads/deletes 不计入」，我们没有那套参数校验与工具白名单，硬凑只会把中间产物、被删文件、读过的文件全当成「交付」。等宿主暴露 change summary 或产物清单接口再接，见 `05` W8 遗留项。

### 5.7 首屏窗口与反向补读（r8 新增）

手机打开会话时**不再全量补齐**。真机 874 条事件按 48 KiB/页要走数十到上百个往返，首屏要等好几秒；而用户 99% 的情况只想看最近发生了什么。

- **窗口按字节定，不按条数定**：先 `POST /session/backfill { beforeSeq: lastSeq + 1, limit: 200, bytes: 98304 }`，由 Host 按**字节预算**裁出「最近一页」，拿到 `toSeq` 后再 `follow(sessionId, { sinceSeq: toSeq })` 接实时流。客户端不再猜窗口起点。
  - 为什么不是固定 50 条：50 条 × 40 KB 的工具结果 = **2 MB**，50 条 × 200 B 的碎片 = **10 KB**，同一数字在两种会话里完全不是一回事。
  - **两个预算，一个旋钮**：页预算 `replayMaxBytes` 默认 48 KiB（`session/follow` 翻页 + `backfill` 翻页共用）；首屏窗口要 **2×（96 KiB）**——开屏只发生一次，多给点内容比多跑一次往返值。窗口预算由客户端在请求里带 `bytes`，**Host 夹在 `[4 KiB, 4× 页预算]`**：客户端要 8 MiB 也只给到 192 KiB。
  - **条数下限 8**：若最新几条都是几十 KB 的巨型事件，纯按预算只剩 1~2 条，一屏都不满、上下文也没了；不足 8 条时允许超预算，但**不超过 4× 该次预算**（防 8 条 × 1 MiB 把帧撑爆）。
  - 索引里没有 `lastSeq`（老数据）时才退回 `follow(-1)` 全量引导补齐。
- **反向补读**：`POST /d/<deviceId>/session/backfill`，请求 `{ sessionId, beforeSeq, limit }`，返回紧邻窗口前面的那一段：

| 字段 | 含义 |
|---|---|
| `events[]` | `seq < beforeSeq` 的最后 `limit` 条（按 `seq` 升序） |
| `fromSeq` / `toSeq` | 本段的起止 seq |
| `hasMoreEarlier` | 最早一条 `seq > 0` 即前面还有；界面据此决定要不要继续显示「加载更早」 |
| `bytes` | 本段字节数（受本次预算约束；请求可带 `bytes` 覆盖，Host 夹在 `[4 KiB, 4× 页预算]`） |

**预算从后往前砍**：超预算时丢的是更早的那些，紧邻窗口的最新几条必须留下——否则用户点十次「加载更早」都看不到紧接着的那几条。

**兼容旧 Host**：旧插件不认 `session/backfill`（白名单内但没实现，回 403 `ENDPOINT_NOT_ALLOWED`）。客户端退回「`follow` 从 `beforeSeq-limit-1` 取一页再筛掉 `>= beforeSeq`」，按钮不会变砖；响应里带 `via: 'follow'` 标明这是降级路径。

**为什么不用 `follow` 硬拉**：`follow` 只能从某点**向后**走，补“更早”会把后面的全部重发一遍；要凑够一屏历史得翻好几页。反向读一次请求就够。

## 7. 权限白名单

```yaml
allowedEndpoints:
  - 'session/*'
  - 'fileUploads/*'   # r3：附件上行；只经 Relay 内存中转，不落盘、不缓存、不进事件流
  - '$events/*'
  # 'session/artifacts'（r6）不需要单独登记：它落在 'session/*' 内，且只回元数据
```
默认拒绝其余一切；高危操作（文件写入、执行命令、读屏）默认全关闭，逐项显式授权后才开放。

**`fileUploads/*` 的边界（r3）**：
- 请求体为 `{ sessionId, data: base64(标准编码), name? }`，`data` 上限由 Relay 的 `maxBodyBytes`（1 MiB）约束，即原始文件约 ≤ 750 KiB。
- 文件内容只在 Relay 进程内**内存中转**（手机 → 自托管 Relay → 本机 Host），**不落盘、不缓存、不写入事件流、不进入 CP**；ADR-010 的「CP/Relay 零正文落盘」口径不变。
- Host 侧调用宿主 `fileUploads`，返回 `receiptId`；`receiptId` 只在接收 Agent 作用域内有效，必须与**同一 session** 的 `session/prompt` 一起使用，不得跨会话复用。
- 文件是否真正进入模型上下文由宿主的 admission 规则决定；本协议不承诺任何媒体类型，类型校验与大小限制归宿主。

**端点归一化（r4）**：白名单比对的是**解码后**的端点，且 `xxx/*` 只放行**单段**（`session/prompt`）。
`session/..%2Fadmin%2Frevoke`、`session/prompt/extra`、`session/%2e%2e/admin` 一律 403 `ENDPOINT_NOT_ALLOWED`。
理由：前缀匹配 `startsWith('session/')` 会把「看起来以 session/ 开头」的穿越串放行给 Host 二次解码，
白名单形同虚设。对应渗透用例 S6。

## 7.1 `/host/*` 的凭据（r4）

`/host/*` 是 Host 侧的管理面，**每个端点独立校验**（它们是独立 HTTP 请求，彼此没有会话关联，
只在注册处查一次等于其余端点裸奔）。配置了 `hostToken` 时必须带，三种载体任选其一：

| 载体 | 形式 | 用在哪 |
|---|---|---|
| 请求头 | `Authorization: Bearer <HOST_TOKEN>` | 推荐；`/host/poll` 等 GET 也用它 |
| 请求体 | `{ "hostToken": "<HOST_TOKEN>" }` | POST 的兼容写法 |
| 查询串 | `?hostToken=<HOST_TOKEN>` | 旧 Host 的降级轮询 |

未配置 `hostToken` 视为**明确的单机开发模式**（`run.mjs` 启动会打警告），不静默放行。

| 端点 | 缺凭据的后果（未加此闸时实测） | 现在 |
|---|---|---|
| `GET /host/poll` | 同网段任何人可读到手机待发的提示词正文与 `reqId` | 401 |
| `POST /host/respond` | 拿到 `reqId` 后可直接伪造 Host 回复，改写手机看到的结果 | 401 |
| `POST /host/sessions` | 可向任意设备的会话列表投毒（伪造行、删行） | 401 |
| `POST /host/heartbeat` | 可把离线设备伪装成在线，让手机持续投递直到全部超时 | 401 |

对应渗透用例 S11–S14。WS 侧 `/ws/host` 的 `host/register` 早已校验同一令牌；
另外升级请求本身不带凭据，因此未注册连接有 `registerTimeoutMs`（默认 10s）硬截止（S10）。
